# 최초 본문 검수 «부분 응답» 후속 요청 (2026-09-23, 뤼튼 실측 F1)

배포 `fb6cc61`로 새로 만든 뤼튼테크놀로지스 보고서에서 본문이 9문장(이전 25문장)만 남고 9장 중 6장이 안내문뿐이었다. 주요 원인 중 하나는 1차 본문 검수의 **부분 응답**이다. 이 문서는 그 실측, 좁힌 원인, 최소 수정, 안전 규칙, 시험을 기록한다. 뉴스 수집 원인은 별도 담당(Astra)이며 여기서 다루지 않는다.

## 1. 실측 (진단 `wrtn-after-diagnostics.json`)

| 단계 | 값 |
|---|---|
| `8_본문검수_응답판독` 시도 1 | 요청번호수 50 · 응답행수 20 · 유효행수 20 · 미응답번호수 30 · 판독 ok · 응답 5,714자 |
| `v2_provider_response` (v2_review) | 종료사유 end_turn (잘림 아님) · 출력상한 24000 |
| `8_본문검수_처분` 판정별 | 참 6 · 근거결속실패_제거 14 · **번호없음_제거 30** |
| 이전 실행(구 코드, 같은 날 03:39) | 참 27 · 번호없음_제거 0 · 생존문장 27 |

응답이 «읽히기는» 했으므로 파싱 재요청 예산(`PARSE_RETRY_LIMIT` = 1)은 쓰이지 않았고, 미응답 30번은 `composer/verify.py`의 처분 단계에서 «검수 미완료»로 그대로 제거됐다(`final[number] = None`). 30건이 새 검수 프롬프트 때문인지 모델 편차인지는 이 자료로 단정할 수 없다. 어느 쪽이든 부분 응답을 한 번도 되묻지 않는 코드는 그대로였다.

## 2. 수정 (feature 내부, `app/src/features/composer/`)

| 파일 | 변경 |
|---|---|
| `verify.py` `_ask_verdicts` | 첫 응답이 읽혔는데 요청 번호 일부의 판정이 없으면(파서가 «미응답»으로 닫은 번호: 행 없음·계약 밖 판정·모순 중복 포함) **빠진 문장만** 다시 묻는다. 조건: `initial_ask`가 있는 최초 본문 검수이고 파싱 재요청을 아직 안 썼을 때(`retries < PARSE_RETRY_LIMIT`). 후속 호출자는 `initial_retry_ask`(없으면 `initial_ask`)이며 후속 검수 호출자 `ask`는 쓰지 않는다 |
| `verify.py` `_merge_review_payloads` (새 함수) | 근거 결속 파서(`constrain_verdicts`·`support_entries_by_number`)가 응답 «원문»의 판정 행을 번호로 다시 읽으므로, 첫 응답의 행은 그대로 두고 후속 응답에서는 후속 대상 번호의 행만 더한 JSON을 `_apply_grounding`에 넘긴다 |
| `verify.py` `REVIEW_JSON_GUIDE` | 첫 프롬프트에 «번호마다 판정 행을 하나씩 빠짐없이 출력한다. 번호를 건너뛰거나 일부만 출력하지 않는다» 안내 88자 추가(무호출 예방). 스키마(`FLAT_REVIEW_SCHEMA`)는 바꾸지 않았다 |
| `constants.py` `MISSING_VERDICTS_REMINDER` | 후속 프롬프트 끝에 붙는 안내. `RETRY_REMINDER`(«직전 응답을 읽을 수 없었다»)와 다르다 — 그쪽을 쓰면 거짓 안내가 된다 |

### 안전 규칙 (모두 시험으로 고정)

- 빠진 번호를 «참»으로 간주하거나 라벨만 바꿔 공개하지 않는다. 후속 응답이 못 읽히거나(형식 오류·빈 응답·호출 오류) 또 빠진 번호는 예전처럼 «번호없음_제거»다. `AskFatalError`는 예전처럼 재전파한다.
- 첫 응답의 판정·검증근거는 한 글자도 바꾸지 않는다. 후속 응답은 후속 대상 번호에만 적용되며, 첫 응답이 이미 판정한 번호(거짓·애매·요청 밖 99 등)를 후속이 덮어쓰지 못하고 후속에서 새로 나온 요청 밖 번호도 버린다.
- 후속으로 회복한 번호도 같은 `_apply_grounding`을 지난다 — 수치 증명·역할 결속·회계 상용구·부재 단언 검사를 우회하지 않는다.
- 호출 상한·최대 출력·회사 비용 상한은 증액하지 않았다. 최초 검수는 여전히 **최대 2회**(첫 요청 + 파싱 재요청 «또는» 누락 후속). 파싱 재요청을 이미 쓴 실행은 부분 응답이어도 후속이 없다.
- 재검수(`_recheck_rewritten`)·요약 검수·묶음(packet) 경로는 `initial_ask`가 없어 예전 그대로 1회다.

### 진단 읽는 법

`8_본문검수_응답판독` 기록이 두 개면: 시도 2의 `요청번호수`가 시도 1과 같으면 파싱 재요청, **시도 1의 미응답번호수와 같으면 누락 후속**이다. 닫힌 관측 계약(shared/report_quality)에 새 칸을 넣지 않았다. 운영 로그에는 `검수 부분 응답 후속: 요청 N · 첫 응답 미응답 M · 후속 판정 회복 K`가 개수만 남는다.

### 후속 호출의 출력 상한

`pipeline/real.py`의 `initial_retry_reviewer_ask`는 «첫 답의 실제 출력 × 1.5, 하한 첫 검수 상한의 절반»으로 상한을 잡는다. 첫 답이 5,714자·20행이었던 이번 사례에도 12,000토큰 하한을 유지한다. 30행 후속을 실제로 수용하고 검증까지 마치는지는 재배포 뒤 실측으로 확인한다. 문자 수만으로 토큰 수나 성공을 확정하지 않는다.

## 3. 시험

새 파일 `composer/tests/test_initial_review_missing_followup.py`(시험 함수 11개 · 매개변수 사례 17개):

- 요청 50·응답 20 → 후속 프롬프트에 빠진 30번만 원래 번호로 실리고 30건 회복, 호출 2회, 관측 [요청 50·미응답 30], [요청 30·미응답 0]
- 첫 응답의 거짓·애매·요청 밖 번호를 후속이 덮어쓰지 못함
- 후속 형식 오류·빈 응답·호출 오류 → 30번 제거, 세 번째 호출 없음; `AskFatalError` 재전파
- 후속 부분 응답(21~30만) → 그만큼만 회복
- 파싱 재요청 뒤 부분 응답 → 후속 없음(예산 소진)
- 후속은 `initial_retry_ask` → 없으면 `initial_ask`, `ask`는 절대 아님; `initial_ask` 없는 일반 경로는 1회 그대로
- 수치 증명이 든 첫 응답이 합친 응답에서도 그대로 검사됨(일치 → 참, 불일치 → 근거결속실패)
- `_merge_review_payloads` 단위: 첫 행 원문 보존(코드 펜스 포함), 후속의 대상 밖·덮어쓰기 행 제거, 숫자 문자열 번호 보정
- `verify_report` 50문장: 후속 성공 시 50 생존·번호없음 0, 후속 실패 시 20 생존·번호없음 30
- 첫 프롬프트 안내 문구

갱신한 기존 시험: `test_initial_review_schema.py`의 «번호누락·계약밖판정·모순중복»은 두 경로 동등성 표에서 빼고 «최초 검수 경로만 후속 1회» 전용 시험으로 옮겼다. `test_review_schema.py`·`test_review_prompt_cache.py`의 평면 경로 프롬프트 바이트 기준선(골든·경계 해시, 고정 접두부 10706→10794)을 안내 88자만큼 갱신했다(묶음 경로 해시는 그대로).

실행: 저장소 루트 `.venv/Scripts/python.exe -X utf8 -m pytest -p no:cacheprovider`, `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1`, 임시 `STORAGE_DB_PATH`·`OBSERVABILITY_RECORDS_PATH`, `app/conftest.py` 유지. `composer/tests` + `shared/report_quality` **3,815 통과·1 skip**. `features/pipeline/tests`는 **1,377 통과**, `local_integration` 표시 2건(실제 CORPCODE.xml 캐시·삼성전자 P01 원문 필요)은 이 워크트리에 그 캐시가 없어 실패했으며 이 변경과 무관하다.

## 4. 한계

- 실제 공급자 호출로 30행 후속이 상한 안에 들어오는지는 재배포 뒤 뤼튼 재실행으로 확인해야 한다(무료 fixture만 검증).
- 후속 응답도 부분이면 남은 번호는 그대로 제거된다 — 두 번째 후속은 예산 규칙상 넣지 않았다.
- 첫 프롬프트 안내 추가로 평면 경로 프롬프트 캐시 접두부가 바뀌어 배포 직후 한 번은 캐시가 새로 만들어진다. 스키마 캐시는 그대로다.
