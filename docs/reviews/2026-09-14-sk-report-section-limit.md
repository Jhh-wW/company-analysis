## 사용자가 정정한 최종 제품 요구

**분석 대상 회사라면 자료가 많든 적든 확보한 내용으로 보고서를 제공한다. 분석 대상이 아닌 경우만 대상 외로 처리한다.** 수집 한도, 일부 문서 누락, 장별 자료 부족은 보고서 전체를 중단시키는 이유로 사용하지 않는다.

아래의 초기 조사와 제안 중 '필수 문서가 미완료이면 전체 작성 차단을 유지한다'는 정책은 사용자의 최신 지시에 따라 철회했다. 미완료 상태를 완료로 바꾸는 대신 보고서에 확인 범위를 표시하고, 확보·검증한 내용을 최대한 담는다. 검증하지 못한 문장은 제외하되 다른 내용은 남긴다. 최종 문서·사실·장 개수 하한 역시 산출물 중단 조건에서 완성도 안내로 바꾼다.

구현 범위는 대형 문서 순회 개선과 함께 대상 판정 이후 수집→사전검사→작성→웹/PDF 출고까지 확대했다. 기존의 차단을 기대하는 테스트도 새 제품 요구에 맞춰 바꾸되, 수치·인용·법인 검증을 통째로 해제하지 않는다. 아래 최초 재현은 과거 코드가 왜 멈췄는지를 설명하는 기록이다.

## 결론

회사 식별과 대상 판정은 지나갔지만, 필수 사업보고서를 나누어 읽는 과정에서 4,096개 구간 제한에 걸렸다. 현재 사전검사 규칙은 필수 DART 문서가 잘린 경우 보고서 생성을 막는다. 따라서 9개 장의 내용이 준비됐다는 `READY_FOR_GENERATION`과 실제 작성 중단이 함께 나타날 수 있다.

이는 사용자가 제공한 로그, 현재 코드, 합성 입력 재현이 일치하는 결론이다. 해당 운영 실행은 확인한 로컬 저장소에서 찾지 못했다. 실제 공시 접수번호·원문·정확한 제목 구간 수·운영 최종 저장 상태를 확보한 것은 아니다.

## 수정 방향

- 제목과 일반 번호 목록을 구분하고, 큰 공시를 순회하면서 필요한 근거를 제한된 크기로 보존하도록 개선한다. 단순 상한 해제는 처리량·메모리 제한을 없애며, 상한 증가만으로는 같은 문제가 재발할 수 있다.
- 필요한 범위만 선택할 경우 어디까지 확인했는지 기록한다. 미검사 문서 전체를 `OK`로 바꾸거나 필수 문서를 선택 사항으로 낮춰 통과시키지 않는다.
- 장별 내용 준비와 최종 작성 허용을 화면에서 구분한다. 이 경우는 ‘일시 장애’보다 ‘공시 문서 처리 상한 초과’라는 안내가 정확하다.
- 실제 실패 공시를 확보해 뒤쪽 근거 보존, 소형 문서 정상 처리, 과도한 제목 입력의 처리량 제한을 함께 검증한다.

## 근본 해결안과 채택 이유

책으로 비유하면 지금은 메모장이 가득 차면 책 읽기도 멈춘다. 바꿀 구조는 책은 끝까지 읽고, 메모장에는 장별로 중요한 내용만 남기는 방식이다. 읽지 못한 페이지가 있으면 그대로 표시한다.

조사 결과 제목 4,096개만 문제가 아니다. 일반 후보 8,192개·4Mi 문자, 고유 줄 색인 32,768개, 짧은 후보 128개·2,048자 등 다른 상한도 순회를 중단시킨다. `collect.py`는 긴 문단과 짧은 관측을 따로 분할하고, 회사 유형 판정용 본문도 모아서 다시 합친다. 따라서 제목 상한만 늘리면 다른 상한에서 다시 같은 문제가 발생할 수 있다.

또한 현재 제목 정규식이 `1.234`, `12.50`, `0.25` 같은 소수를 제목으로 판정하는 것을 재현했다. XML 태그를 개행으로 바꾸는 추출 방식에서는 표의 숫자가 독립 줄이 될 수 있다. 다만 실제 SK 실패 원문을 확보하지 못했으므로 소수 오인이 이 실행의 상한 초과를 일으켰다고 단정하지 않는다.

| 방법 | 판단 |
|---|---|
| 상한을 크게 늘리기 | 다른 개수·문자·메모리 한도에서 재발할 수 있어 근본안으로 채택하지 않음 |
| 9개 장이 준비됐으니 잘린 필수 문서도 허용하기 | 뒤쪽의 취소·위험·조건 변경을 읽지 못한 상태를 통과시키므로 채택하지 않음 |
| **끝까지 순회하고 근거 보관량만 제한하기** | **우선 구현안. 끝부분도 검토하며 메모리와 작성 입력량을 제한할 수 있음** |
| XML 제목·표·본문 구조를 보존하기 | 유용한 후속 개선. 정규화 원문과 좌표·해시가 바뀌므로 별도 회귀 검증 필요 |

### 읽기와 보관을 분리하는 동작

1. 원문 위치를 가진 후보를 하나씩 내보내고 즉시 채점한다. 현재 정규화 원문 표현은 유지하며, 모든 제목·문단 객체를 먼저 목록에 쌓지 않는다.
2. 장·의미 칸별로 근거를 보관한다. 특정 장의 문단이 많아도 다른 장의 근거를 밀어내지 않으며, 뒤에서 더 적합한 근거가 나오면 교체한다. 기간·대상·문서 위치의 다양성과 뒤쪽의 변경·취소 문맥을 검증한다.
3. 반복 줄 색인이나 후보 보관 한도가 찼다는 이유로 원문 순회를 멈추지 않는다. 보관하지 않은 개수와 범위는 진단으로 남긴다. 무분류 후보를 모두 보관하지 못했다면 이를 회사의 자료 부재로 해석하지 않는다.
4. 원문 좌표, 본문·조각 SHA256, 인용·법인 결속을 유지한다. 서로 다른 표 셀이나 문단을 임의로 이어 붙여 원문을 만들지 않는다.
5. 실제 바이트·시간·파싱 한도는 유지하고 순회 중에도 마감을 검사한다. 입력 크기나 시간 때문에 끝까지 읽지 못했다면 완료로 표시하지 않는다.

### 구분해야 하는 세 가지 상태

| 상태 | 답하는 질문 |
|---|---|
| 원문 순회 상태 | 받아들인 원문 범위를 끝까지 살폈는가? 중단했다면 어디서, 왜 멈췄는가? |
| 후보 보관 상태 | 살펴본 후보 가운데 보관 예산 때문에 제외한 내용이 있는가? |
| 작성 근거 준비 상태 | 실제로 남긴 검증 근거가 각 장을 작성하기에 충분한가? |

원문을 끝까지 순회했다는 것은 모든 의미를 완벽하게 이해하거나 모든 주장을 검증했다는 뜻이 아니다. 후보 압축도 의미 검증을 대신하지 않는다. 필수 원문이 실제로 미완료인 경우의 차단은 유지한다.

자료 계약은 엔진 모델·직렬화, 앱 어댑터·정규화, 공통 모델, 수집 스냅샷과 캐시 지문까지 연결되어야 한다. 엔진에만 상태를 추가하면 앱에서 사라질 수 있다. 상태가 다른 자료가 같은 캐시로 취급되거나, 옛 캐시가 새 읽기 완료 증명으로 승격되지 않도록 검증한다.

### 검증과 운영 적용의 범위

- 4,096개를 넘는 제목과 8,192개를 넘는 문단 뒤에 유일한 필수 근거를 넣어 보관 여부를 확인한다.
- 특정 장의 많은 문단, 뒤쪽 변경·취소, 소수와 번호 목록, 고유 줄 색인 포화, 무분류 보관 한도를 검사한다.
- 가짜 시계로 문서 중간 시간 초과를 만들고 미완료 상태와 작성 차단이 유지되는지 확인한다.
- 선택된 모든 후보의 원문 좌표·해시 및 자료 계약 직렬화·복원·봉인·버전 호환을 확인한다.
- 작은 정상 문서의 기존 행동과 앱의 관련 회귀 시험을 실행한다.
- 실제 실패 공시 원문을 확보한 재실행과 운영 배포는 별도의 검증 단계다. 합성 시험 통과만으로 해당 SK 실행의 실제 재성공을 선언하지 않는다.

현재 입력 한도인 문서 8MiB·수집 합계 24MiB와 기본 수집 45초를 무제한으로 늘리는 계획이 아니다. 이 범위에서도 실제 SK 공시가 시간 안에 처리되는지는 측정해야 한다. 부족할 때에는 원문 해시와 재개 위치를 결속한 후속 처리 방안을 검토하며, 시간 제한을 숨기거나 자동으로 유료 호출을 반복하지 않는다.

### 병렬 작업 배정

- Codex Astra: SK 수집 구조와 필요한 앱 계약·진단의 운영 코드 구현 및 회귀 시험.
- Claude FABLE / max: 독립 반례 재현과 설계·변경 검토. 운영 코드는 수정하지 않는다.
- 총괄 Codex: 제안 비교, 경계 계약 점검, 독립 검증, 문서와 최종 결과 정리.

실행 영수증에서 Astra의 `model=gpt-6-astra`, Claude의 `model=fable`, `effort=max` 적용을 확인했다. 두 작업자는 같은 작업 폴더에서 소유 파일을 구분하여 병렬 진행한다.
