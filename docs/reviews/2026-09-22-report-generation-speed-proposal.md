**1순위: 장별 작성 3개 동시 실행**

장별 근거 묶음이 준비된 경로에서 최대 3개 작업을 유지하고, 하나가 끝나면 다음 장을 시작한다. 세 장이 모두 끝날 때까지 다음 묶음을 기다리는 방식보다 긴 장의 영향을 줄일 수 있다. 결과는 완료 순서와 무관하게 기존 목차 순서로 조립한다.

9개의 작성 호출, 각 장의 입력, 모델, 출력 상한, 원문 좌표·지문·인용 허용 범위는 유지한다. 전체 본문·도식 검수, 장 간 중복 제거, 요약 결속, 수치 검증과 공개 검사는 기존 합류 지점에서 그대로 수행한다. 장별 작업 시간이 비슷하고 공급자 제한에 걸리지 않으면 작성 구간의 이론적 시간은 약 1/3이다. 보고서 전체가 자동으로 1/3이 된다는 뜻은 아니다.

먼저 해결할 사항은 다음과 같다.

- `composer/pipeline.py:311`의 호출 장부는 `len(self._records) + 1`로 순번을 만들고 호출 후 기록한다. 장 번호도 호출 진입 순서에 의존한다. 장 ID·호출 ID를 작업 시작 전에 확정하고, 완료 기록은 안전하게 모아야 한다.
- `pipeline/real.py:1018`의 단계·캐시·잔여 호출 예약은 같은 엔진 객체를 변경한다. 호출별 불변 문맥으로 분리하고 금액·호출 수 예약과 실제 정산을 원자적으로 처리한다. 네트워크 대기 전체를 잠그면 동시 실행 효과가 없으므로 예약·기록 구간만 보호한다.
- 스레드로 넘기는 취소·실행 소유권·공급자 시도 문맥도 보존한다. `ContextVar` 복사만으로 내부의 공유 가변 객체가 분리되지는 않는다.
- 서버는 현재 최대 보고서 5건을 동시 처리한다(`app/src/core/constants.py:17`). 보고서마다 3개 호출을 허용하면 작성 요청이 최대 15개 겹칠 수 있으므로 서버 전체 공급자 요청 제한과 공정한 배분이 필요하다.
- 부분 전환 경로의 앞 장 의존성을 별도로 계측한다. 장별 작성 계획·사실 소유권을 생성 전에 고정하는 설계로 전환하려면 기존 결과와 품질을 비교한다. 단순히 앞 장 문장을 지워서 동시 실행하지 않는다.

호출 장부는 현재 코드의 실제 `_CallLedgerRecorder`에 외부 통신 없는 가짜 호출 3개를 동시 주입해 확인했다. 각 가짜 호출을 `Barrier(3)`에서 합류시킨 결과, 기록 3개의 `sequence`는 **[1, 1, 1]**이었다. 이는 현 순차 운영에 이미 오류가 있다는 뜻이 아니라, 현재 기록기를 그대로 병렬화하면 계약이 깨진다는 재현이다. 성능이나 보고서 품질을 측정한 시험은 아니다.

공급자는 요청 수와 입력·출력 토큰 처리율을 각각 제한하므로 동시 실행 수를 늘려도 한도에 걸리면 단축되지 않는다. 적용은 1→2→3 순서로 비교하며 실제 사용량·429 응답·대기 시간을 기록한다. [Anthropic 호출 제한 문서](https://platform.claude.com/docs/en/api/rate-limits)

**2순위: 뉴스 본문 수집 대기를 겹치기**

`news_intake/collection.py:146` 이후의 후보 순회에서 같은 기간·분석 묶음에 이미 선택된 기사만 2~3개씩 미리 읽는다. 같은 도메인은 낮은 동시 실행 한도를 두고, 받은 결과는 기존 후보 순서로 소비한다. 기사 수·기간별 배분·원문 문자 예산·발행일·회사 일치·신뢰 매체·robots·주소 안전 검증은 유지한다.

기사 분석 결과가 다음 기간 확장과 조기 종료를 결정하므로 모든 기간의 후보를 한꺼번에 요청하지 않는다. 다음 분석 묶음으로 무제한 선행 요청하지 않고, 사용하지 않은 선행 요청까지 호출 한도와 진단에 포함한다. 이미 출발한 요청은 취소해도 실제 실행됐을 수 있으므로 성공·실패·취소를 모두 정산한다. 수집 구간의 절반 단축은 목표이며 서버 응답과 후보 구성에 따라 달라진다.

기존의 비교 조사·뉴스 검색 동시 실행과 이 효과를 중복 계산하지 않는다. 공식 수집 결과가 뉴스 회사 식별과 호출 예산에 사용되므로, 뉴스 전체를 공식 조사보다 먼저 시작하는 변경은 이번 우선안에 포함하지 않는다.

**3순위: 변경되지 않은 중간 산출물의 재사용 범위 확인**

이미 있는 보고서 캐시와 문서 다운로드 재사용을 먼저 측정한다. 추가로 원문 해시·파서 버전·법인·기준일·정책 버전이 같은 근거 추출 산출물을 재사용할 수 있는지 확인한다. 정정 공시, 새 뉴스, 출처 상태 변경이 있으면 관련 결과는 다시 수집·검증한다. 중단된 부분 수집을 완료 상태로 재사용하지 않는다.

이는 같은 회사의 반복 요청에 유리하며, 처음 분석하는 회사의 절반 단축 계산에는 넣지 않는다. 회사 이름만 같다는 이유로 과거 PDF를 최신 보고서로 돌려주는 방식은 품질 조건을 충족하지 않는다.

프롬프트 캐시도 추가 효과를 따로 측정한다. 현재 전체 근거 경로는 공유 접두부를 사용하지만 장별 근거 묶음 경로는 근거가 서로 다르다. 캐시를 위해 다른 장의 근거를 합치면 근거 경계가 달라진다. 공통 지시문을 재사용하더라도 정확히 일치하는 접두부와 최소 길이가 필요하고, 동시 요청은 첫 응답이 시작되기 전까지 같은 신규 캐시를 읽을 수 없다. [Anthropic 프롬프트 캐시 문서](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

**절반 단축이 가능한 조건**

전체 시간 중 3개 동시 실행 가능한 작성 비중을 `p`, 절반으로 줄일 수 있는 수집 비중을 `q`, 새 대기·정산 부담의 비중을 `h`라고 두면 다음과 같다. 두 구간은 겹치지 않는 기존 경과시간을 기준으로 계산한다.

`개선 후 시간 / 기존 시간 ≈ 1 - (2/3 × p) - (1/2 × q) + h`

작성만 바꿀 경우 작성 비중이 75% 이상이어야 추가 부담이 없는 이상적 조건에서 전체 절반이 가능하다. 검수나 복구가 대부분인 실행, 앞 장 의존 경로가 많은 서비스에서는 이 방안만으로 절반을 달성했다고 할 수 없다.

**품질을 유지했다고 인정할 기준과 적용 순서**

1. 최신 운영 실행을 FULL/부분 전환, 최초/재사용, 단독/동시 사용자로 나눠 기준선을 만든다. 회사 확정부터 검증된 웹·PDF 공개 완료까지 측정하며, 대기와 실패·재시도 시간을 제외하지 않는다. 성공 사례만 골라 시간 개선을 계산하지 않는다.
2. 기존 단계 시간에 장별 작성, 공급자 대기, 입력·출력 토큰, 뉴스 본문 다운로드, 검수, 복구, PDF 시간을 연결한다. 각 호출의 시간 합과 병렬 구간의 실제 경과시간은 분리한다.
3. 동일 근거 스냅샷에서 기존/변경 실행을 비교한다. 장별 입력 해시·작성 호출 수·모델·출력 상한·검증기 설정이 같은지 먼저 확인한다. 완료 순서 뒤집힘, 중간 오류, 취소, 비용 한도 소진을 오프라인에서 재현한다.
4. 상장사·비상장 감사법인·대형 공시·뉴스가 적은 회사·부분 전환 사례를 포함한 고정 평가군으로 비교한다. 최초 10개 회사 정도를 시작점으로 삼되 이를 통계적 품질 동등성의 증명으로 과장하지 않는다. 같은 원문과 기준일을 사용하고 생성 변동을 고려해 반복 비교한다.
5. 회사·수치·단위·기간·인용 결속의 중대 오류가 없어야 한다. 핵심 사업 설명·유효 사실·자료 출처의 범위, 장별 빈칸, 중복, 요약의 본문 결속, 웹/PDF 완성도를 확인한다. 내용을 덜 생성하거나 더 많이 삭제해 빨라진 결과는 개선으로 통과시키지 않는다. 문장 수나 자동 시험 통과만으로 읽기 품질을 판정하지 않는다.
6. 같은 운영 조건에서 전체 완료 시간 중앙값과 상위 10% 경계값을 각각 기존의 50% 이하로 만드는 것을 목표로 둔다. 실패·재시도·비용 증가도 함께 공개한다. 중앙값만 달성하면 중앙값 개선으로만 보고한다. 새 동시 실행 스위치를 1→2→3으로 올리고 품질이나 꼬리 지연이 나빠지면 1로 복귀한다.

작성 동시 실행부터 검증하고, 수집 개선을 더한 뒤 절반 목표를 판정하는 순서가 적절하다. 기존 검수 1회를 여러 호출로 나누는 변경은 전역 문맥과 FULL 호출 계약에 영향을 주므로, 검수가 주된 병목으로 측정될 때 별도 설계한다.

기존 [프롬프트 비용 개선 기록](2026-09-13-prompt-cost-implementation.md)의 입력 공백 제거 효과는 작은 수준이었다. 이를 주요 속도 개선으로 확대 해석하지 않는다. 미검증 본문을 먼저 노출하는 진행 표시, 출력 토큰 상한 축소, 조사 기간·출처 축소, 검수 생략 역시 이번 품질 유지 목표의 대체 수단으로 삼지 않는다.
