# 품질과 생성 속도를 유지하는 비용 절감 제안

2026-09-22 · 코드 `7a15b073` · 구현 전 분석

**동시 실행 자체는 토큰 단가를 올리지 않는다. 같은 모델·실제 사용량·캐시 적중·호출 수라면 AI 비용도 같다.** 그러나 캐시가 만들어지기 전에 같은 입력을 여러 번 처리하거나, 취소·오류 뒤 불필요한 요청까지 진행하면 비용이 늘 수 있다. 따라서 [속도 개선안](2026-09-22-report-generation-speed-proposal.md)에 캐시 보존과 총비용 비교를 함께 적용해야 한다. 서버 증설비는 AI 토큰 비용과 별도로 계산한다. [공식 요금표](https://platform.claude.com/docs/en/about-claude/pricing)

이번에는 코드·과거 비용 기록을 읽고, 외부 통신 없는 프롬프트 길이와 요금 산술을 확인했다. 운영 생성·배포·설정 변경은 하지 않았다. 최신 평균 원가나 절감률을 실측한 결과는 아니다.

**확인한 비용 구조**

[9월 13일 현대글로비스 조사 기록](2026-09-13-prompt-cost-implementation.md)에 있는 운영 실행 1건의 내부 AI 원가다. 현재 전체 서비스 평균이나 공급자 결제 총액으로 해석하지 않는다.

| 단계 | 호출 | 기록된 원가 | 비중 |
|---|---:|---:|---:|
| 본문·요약 작성 | 10회 | 429.40원 | 59.5% |
| 본문·도식 검수 | 2회 | 207.91원 | 28.8% |
| 뉴스 분석 | 3회 | 84.30원 | 11.7% |
| 합계 | 15회 | 721.61원 | 100% |

이 실행은 전부 Haiku 4.5였다. 현재 v2 작성도 `pipeline/real.py:1567`에서 불러오는 `analysis_engine/tools/run_pilot.py:85`의 Haiku를 기본으로 사용하며, 공급자 직전에는 요청 엔진의 모델을 우선한다. `app/src/core/constants.py`에 Sonnet 기본값이 있다고 해서 실제 v2 비용을 Sonnet 가격으로 계산하면 안 된다. 최종 근거는 호출 사용량의 실제 응답 모델이다.

과거 실행에는 작성 캐시 생성 72,086토큰과 읽기 576,688토큰이 있었다. 이미 캐시·번호 선택 요약·검수 원문 중복 제거·수치 원문 참조가 있으므로 이를 새 절감으로 더하지 않는다. 공백 제거의 과거 시험 효과도 약 0.12원으로 작았다.

**동시 실행 비용 증가를 막는 방법**

공유 입력을 캐시로 읽으려면 첫 응답이 시작돼 캐시가 준비된 뒤 후속 호출을 보내야 한다. 해당 입력이 실제로 동일한 경우에만 적용한다. 장별 근거가 다른 FULL 작성에는 공유 원문 캐시가 없으므로, 캐시를 만들려고 다른 장의 근거를 합치지 않는다. 앞 장 생성문에 의존하는 기존 작성 경로도 그대로 동시 실행할 수 없다. [공식 캐시 동시 요청 조건](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

7만 2,086토큰의 같은 접두부를 9번 사용하는 가정으로 앱 요금 함수를 실행했다. Haiku 4.5와 앱의 고정 환율 1달러=1,400원, 5분 캐시를 사용했다. 아래는 **공유 입력 부분만의 산술 예시**이며 실제로 지출한 비용이나 공급자가 중복 쓰기를 반드시 과금한다는 예측이 아니다.

| 캐시 사용 가정 | 공유 입력 비용 |
|---|---:|
| 1번 생성 + 8번 읽기 | 206.89원 |
| 3번 생성 + 6번 읽기 | 439.01원 |
| 9번 생성 + 읽기 없음 | 1,135.36원 |

첫 사례에서 둘째 사례로 바뀌면 같은 입력에 약 232원이 더 든다. 이것이 캐시 준비를 고려하지 않은 병렬화를 피해야 하는 이유다. 실제 배포에서는 `cache_creation_input_tokens`, `cache_read_input_tokens`, 일반 입력·출력 토큰을 확인한다. 별도 캐시 준비 요청도 유료이며 호출 한도와 장부에 포함해야 한다. 가능하면 원래 필요한 첫 호출을 활용한다.

**1. 검수 지침 캐시: 가장 먼저 적용할 저위험 후보**

현재 `_build_review_prompt`와 `_build_grouped_review_prompt`는 고정 지침으로 시작하지만 일반 문자열을 돌려준다. `_v2_ask_via_provider`는 `cache_prefix_chars`가 있는 경우만 명시적 캐시 블록으로 전달한다. `ReviewPrompt`도 현재는 재요청용 응답 스키마만 보관한다.

실제 모듈에서 초기 `parts` 목록을 평가한 오프라인 확인 결과는 다음과 같다. **문자 수이며 API 토큰 수가 아니다.**

| 검수 형식 | 고정 지침 접두부 길이 | 현재 프롬프트 캐시 경계 |
|---|---:|---:|
| 일반 본문 검수 | 10,580자 | 0 |
| 장별 본문·도식 묶음 검수 | 11,722자 | 0 |

기존 지침을 바꾸지 않고 이 접두부 끝에 캐시 표식을 붙이는 것이 첫 후보다. 두 형식은 서로 다른 접두부로 취급한다. 응답 스키마가 붙는 재요청에서도 메타데이터가 정확히 전달되는지 확인한다. 스키마·모델·설정이 달라 캐시가 깨지는 경우는 따로 센다.

Haiku 4.5의 5분 캐시는 생성이 일반 입력의 1.25배, 읽기가 0.1배다. 동일 부분을 유효시간 안에 2번 사용하면 그 부분의 합계는 캐시 없이 처리할 때보다 32.5% 작고, 10번이면 78.5% 작다. 한 번만 사용하면 오히려 25% 비싸다. 최소 캐시 길이 4,096토큰도 충족해야 하므로 문자 수만 보고 적용 효과를 확정하지 않는다. 트래픽이 드물면 유료 사전 준비를 반복하지 않는다. 이것은 **캐시 가능한 입력 부분**의 절감이며 검수 전체 원가나 보고서 전체 원가의 절감률이 아니다. [공식 캐시 요금·최소 길이](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

**2. 장별 근거 전달: 처음 만드는 보고서의 비용 절감 후보**

`composer/logic.py:1499`는 FULL에서 장별 근거 묶음을 사용하지만, 기존 경로는 전체 근거를 장마다 전달하고 앞 장 생성문까지 누적한다. 자료가 부족해 부분 경로로 전환될 때도, 확인된 사실을 장별로 배정할 수 있는지 검토한다. 자료가 부족한 장을 억지로 채우거나 근거를 짧게 잘라 같은 묶음으로 만드는 방식은 사용하지 않는다.

계산은 현재 캐시 할인까지 반영한다. 같은 근거 `P`토큰을 9번 전달할 때 1번 생성·8번 읽기가 되면 비용은 일반 입력 `2.05P`토큰에 해당한다. 장별 배분 후 일반 입력 토큰 합이 `P`라면 이 근거 입력 부분의 절감은 약 51.2%다. **입력량이 9분의 1이 됐으니 비용도 9분의 1이라는 계산은 틀리다.** 실제로는 여러 장에 필요한 문맥, 지침, 이전 문장 제거에 따른 중복 제어 변화가 있어 토큰 합과 품질을 비교해야 한다.

FULL에 이미 적용된 이점은 추가 절감으로 잡지 않는다. 부분 경로에는 빈 장·허용 주장·원문 결속 계약을 별도로 설계해야 하므로 캐시 표식 추가보다 검증 범위가 크다.

**3. 장별 작성 결과 재사용: 반복 생성에서 가장 큰 후보**

현재 `pipeline/news_research_context.py:71`은 새 뉴스 스냅샷·기준일을 전체 생성 지문에 포함한다. 최신성 보존에 필요한 계약이다. 완성 보고서 캐시만으로는 일부 자료가 달라진 경우까지 재사용하기 어렵다.

장별로 최종 입력·근거·모델·생성 설정·프롬프트 버전·관련 기준일의 지문을 묶고, 이 값이 같은 장의 성공한 작성 결과만 재사용한다. 새 자료가 해당 장의 전제·기간·반대 근거에 영향을 주면 재사용을 취소한다. 부분 작성·검증 실패·출력 잘림을 정상 결과로 저장하지 않는다. 사용자 공고 등 맞춤 입력이 있으면 그것도 열쇠에 넣는다.

새로 작성한 장과 재사용 장을 모아 **현재 자료에 대한 전체 검수, 사실 소유권·중복 제거, 요약 결속, PDF 검사를 다시 수행**한다. 9장 중 1장만 바뀌고 나머지 8장의 작성 입력이 정말 같다면 그 8장의 작성 호출을 아낄 수 있다. 검수 비용까지 8/9 줄었다고 계산하지 않는다. 새 회사의 최초 요청에는 효과가 없다.

FULL의 현재 호출 장부는 실제 9회 작성 계약을 갖고 있다. 캐시 적중을 가짜 AI 호출로 기록하지 말고, 재사용 원본의 입력·응답 지문과 현재 검증 회차에 결속된 영수증으로 계약을 확장해야 한다. 웹/PDF 권한·현재 출고 승인은 별도로 유지한다.

**4. 검수 응답의 반복 원문을 줄이기**

Haiku 4.5는 일반 입력 100만 토큰당 1달러, 출력은 5달러다. 따라서 반복되는 검수용 출력도 절감 대상이다. 현재 `numeric_quote_refs.py`는 같은 수치 배열 안에서 원문을 참조하는 기능이 이미 있다. 추가 후보는 다른 검증 배열에서 반복되는 원문에 원문 위치·조각 ID를 부여하고, 기존 검증기 앞에서 정확히 되돌리는 방식이다. [공식 Haiku 요금](https://platform.claude.com/docs/en/about-claude/pricing)

원문·수치·기간·주체 관계를 검증하는 정보는 그대로 유지한다. 모델에게 임의의 긴 원문을 베끼게 하는 대신 미리 부여한 정확한 원문 구간 ID를 선택하게 할 수 있으나, 구간 선택 오류와 주위 문맥 누락을 평가해야 한다. 단순히 검수 이유·근거 배열을 삭제하거나 근거 전체 조각을 자동 정답으로 채워 넣지 않는다. 출력 상한만 낮추는 것은 절감이 아니라 잘림과 재시도를 만들 수 있다.

이 단계는 내부 표현 계약을 바꾸므로 위 1번보다 위험하다. 기존 원문 참조 절감분과 중복 계산하지 않고, 실제 출력 토큰과 근거 유지율을 비교한 뒤 채택한다.

**5. 사전 생성·평가의 할인 배치**

공식 Message Batches API는 표준 API 대비 토큰 요금이 50%다. 그러나 완료까지 최대 24시간이 걸릴 수 있고 처리 기한 내 완료되지 않는 요청도 있어 즉석 보고서에 적용하면 속도 목표와 충돌한다. 수요가 확인된 사전 생성이나 고정 평가 자료에 한정한다. [공식 배치 계약](https://platform.claude.com/docs/en/build-with-claude/batch-processing)

작성→검수의 의존성을 유지하고 완료 후에도 같은 검사를 수행한다. 배치에서 캐시 적중이 나빠지거나 사용되지 않는 보고서를 많이 만들면 총비용은 오히려 늘 수 있다. 따라서 721.61원의 운영 사례가 무조건 360.81원이 된다고 예측하지 않는다. 사전 생성 결과의 기준일을 표시하고 새 자료가 있으면 해당 부분을 갱신한다. 할인 산술 함수는 이미 있지만, 공급자 호출·비용 원장·비동기 상태·출고 계약을 연결하는 구현은 별도다.

**품질·비용 판정과 실행 순서**

실행은 캐시 손실 방지와 검수 지침 캐시부터 시작한다. 다음으로 실제 사용 비중이 큰 경로를 선택해, 최초 생성이 많으면 장별 근거 전달·반복 출력 축소를, 같은 회사 재요청이 많으면 장별 작성 재사용을 적용한다. 이미 작은 모델을 쓰는 상황에서 모델을 더 낮추는 것은 우선안이 아니다.

같은 회사·기준일·원문을 고정하고 변경 전후를 비교한다. 중대 사실·수치·인용 오류, 핵심 사업 설명 누락, 장별 자료 범위, 중복, 요약, 웹/PDF 품질이 악화되면 절감으로 인정하지 않는다. 결과를 덜 쓰거나 검수 탈락분을 더 많이 지워 비용을 줄이는 것도 통과시키지 않는다. 형식 실패를 줄이되 기존 검증 기준은 유지한다.

건당 총 AI 원가는 성공 호출만 세지 않고 실패·재작성·캐시 준비·사용되지 않은 사전 생성까지 포함한다. 최초/반복, FULL/부분, 캐시 적중/미적중별로 완료 시간 중앙값·상위 10% 경계값과 함께 기록한다. 공급자 청구, 앱 원화 원가, 고객 청구, 서버 비용을 구분한다.

현재 자료만으로 서비스 전체의 30% 또는 50% 비용 절감을 보장할 수는 없다. 다만 **동시 실행의 비용 증가를 막고, 바뀌지 않은 입력·장·원문을 다시 처리하지 않는 방향**은 품질과 속도 목표에 함께 맞는다. 확보한 비용 항목별 실측으로 순차 채택하며 절감률을 합산해 과장하지 않는다.
