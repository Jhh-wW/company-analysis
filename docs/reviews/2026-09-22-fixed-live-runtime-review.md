## 재판정 소유권과 캐시

정적 검토한 호출 순서는 무료 캐시 조회 → 재판정 전용 준비 lease 획득 → 캐시 재조회 → 계량 provider 호출 → 결과 저장 → 공식 근거 사전검사 → 최종 생성 모드·입력 지문·보고서 lease 확정이다. [재판정 단계](../../app/src/features/pipeline/evidence_reclassify_step.py)의 `_reclassification_connection`과 [생성 세션](../../app/src/web/generation_singleflight.py)의 `paid_preparation`이 이를 나누어 처리한다.

캐시 키에는 접수번호·프롬프트 버전·모델뿐 아니라 실제 후보 원문/위치, 프롬프트, 회사, 기존 문서·조각 배정의 지문이 들어간다. 준비 lease의 입력 지문도 같은 키다. 수집 시도·스캔 완료 상태만 바뀐 경우에는 분류를 다시 유료 호출하지 않고 현재 수집 상태로 병합한다. 대기자는 owner의 완료 후 캐시를 다시 읽으며, 결과가 없을 때 중복 호출하지 않는다. 저장 실패 시에는 owner만 새 배정을 사용하는 일이 없도록 저장 결과를 재확인하거나 원래 근거로 돌아간다. 이 구조는 소스 검토이며 이번에 동시 요청을 새로 발생시켜 검증한 것은 아니다.

시간 해석은 [HTTP 평가기](../../app/tools/evaluate_companies.py)와 [단계 계측 코드](../../app/src/features/pipeline/real.py)를 대조했다. `elapsed_wall_seconds`는 `/confirm` 직전의 `time.time()`부터 최종 원장·진단 내보내기·결과 GET까지이며 PDF 다운로드와 PDF 분석은 제외한다. 서버 시간은 `final_record_json.elapsed_sec`다. lifecycle 바깥 열의 `elapsed_sec=0.9`는 초기 확인 단계의 누적값이 보존된 것으로, 전체 실행 시간으로 사용하면 안 된다. `collect`/`generate`는 단조 시계의 단계 전환 계측이며, 최초 9장 작성 시간은 생성 단계 안의 부분 구간이므로 서로 더하지 않는다. 재판정 단독 고해상도 타이머는 없고 전송·응답 기록상 약 5초다.

## 비교의 한계와 남은 검증

세 실행의 기준일, DART 접수번호 5개, 재무 payload 지문은 같았다. 재무 지문은 `803fd539f9223fbab42f24a5547d5a08ddb0600238409afbe3cfb7ca50932c3d`다. 그러나 수정본 뉴스 검색 스냅샷은 이전 두 실행과 다르다. 뉴스 본문은 33,423자 / 33,353자 / 31,408자, 뉴스 근거 조각은 4 / 5 / 2개다. 재판정이 실제 호출예산을 먼저 사용하면서 이번 뉴스 분석 상한·실제 호출도 4회에서 3회로 달라졌다. 최종 사전 입력 지문 역시 이전 두 실행과 다르다.

따라서 같은 원문을 재생한 통제 실험이 아니며, 소스 수정·뉴스 입력·검수 응답 및 재시도가 함께 달라졌다. 관측된 시간·비용 차이를 재판정 수정이나 병렬화 하나의 효과로 귀속하지 않는다. 최초 flat 작성의 프롬프트·packet 지문을 이번 산출물만으로 이전과 동일하다고 증명하지도 않는다.

확인하지 않은 것은 동시 owner/waiter 실호출 경쟁, 재판정 캐시 적중 시 무호출, 준비 비용 발생 뒤 최종 보고서 재사용·취소·장애 정산, FULL 실제 작성과 3장 동시 처리의 효과다. 관련 방어 코드와 기존 회귀 시험 소스는 읽었지만 이번 감사에서 시험을 실행하거나 추가 유료 요청으로 그 경로를 재현하지 않았다. 보고서 문장·표의 정확성과 PDF 시각 품질은 별도 내용 검수 대상이다. 이 문서는 런타임 정상 완료와 원가 정합성을 확인하며, 품질 동등성이나 운영 배포 적합성의 합격 증거로 사용하지 않는다.

## 실행 완료 후 별도 배정된 시점 검수 수정

20:23 KST의 후속 배정으로 [grounding.py](../../app/src/features/composer/grounding.py), 새 [plan_timing_guard.py](../../app/src/features/composer/plan_timing_guard.py)·[상수](../../app/src/features/composer/plan_timing_constants.py), [회귀 시험](../../app/src/features/composer/tests/test_plan_timing_guard.py)을 수정했다. 측정된 실행에 적용된 소스와 구분해야 한다. 기존 보고서·PDF는 바꾸지 않았고 추가 유료 생성은 하지 않았다.

실제 6·9장의 `2025년 사업 개시 … 목표로 … 진행 중` 문장을 재현했다. 보고서 기준일이 2026-09-22인데 지난 목표를 현재 예정으로 제시하는 문제다. 새 검사는 기준연도보다 앞선 명시 목표연도, 개시·준공·출시 등 제한된 목표 사건, 그 목표에 연결된 현재 진행·예정 표현이 함께 있을 때 `plan_target_year_outdated`로 거절한다. 사실이나 날짜를 자동으로 고쳐 쓰지 않는다. 기존 `baseline_date` 전달 경계를 사용하므로 새 API 호출이나 별도 검수 요청이 없다.

명시적인 과거 진행형, 과거 기준을 갖춘 인용, 미달·연장·연기·중단 설명, 당년·미래 목표는 새 검사가 거절하지 않는다. 같은 문장 안의 별도 현재 주장까지 과거 낱말 하나로 면제하지 않는다. 최신 원문 예외는 기준연도의 현재 시점 표기와 같은 주장이 같은 문장에 있을 때만 공백·문장부호를 정규화해 확인하며, 게시일·다른 문장의 현재 표지·미래 날짜·부정문·과거 인용으로 대체하지 않는다. 기존 역할·인과 검수 등 다른 근거 요건은 유지한다.

수정 전 실제 문장 포함 회귀 두 건의 실패를 확인했다. 최종 시험은 새 시점 회귀, `test_temporal_grounding_review.py`, `test_grounding.py`, `test_baseline_date_wiring.py`, `test_future_gate_year_and_trend.py`, `test_grounding_rewrite.py`, `test_future_plan_integration.py`를 저장소 `.venv/Scripts/python.exe -X utf8 -m pytest`로 실행해 **205건 통과**했다. 실제 `verify_report`의 flat·packet 경로와 렌더 결과에서 지난 목표 문장이 사라지고 미래 목표는 보존되는지, 주입 검수 호출이 1회로 유지되는지도 확인했다. 전체 테스트 실행이나 실제 유료 재생성 결과가 아니다.

검사는 좁은 문형에 한정된다. 같은 해 안에서 지난 월·일, 생략되거나 두 자리로 적힌 목표연도, 원문과 다르게 풀어 쓴 최신 상태의 의미 동등성, 여러 도식 칸을 합쳐야 드러나는 목표 시점은 이번 변경으로 판정하지 않는다. 날짜 없는 요청에는 현재 연도를 추정해 넣지 않는다. 기존 산출물의 내용·시각 품질과 후속 수정본의 실제 시간·원가는 여전히 별도 검증 대상이다.
