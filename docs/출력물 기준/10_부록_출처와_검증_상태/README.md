# 부록. 출처와 검증 상태

## 이 장의 목적

본문의 모든 사실이 어느 원문에서 왔는지 독자가 직접 추적할 수 있게 한다. 자료의 발행 주체·시점·위치와 사실 상태·검증 상태를 분리해 보여줘 `실제`, `잠정`, `계획`, `추정`, `검증 완료·부족`을 서로 섞지 않는다.

이 장은 제작 과정 설명이 아니다. 조사 방법, 사용한 AI·에이전트, 50개 레퍼런스 분석, 내부 검수 절차는 완성 보고서에 넣지 않는다.

## 이 장이 답해야 하는 질문

1. 본문의 `[번호]`가 정확히 어떤 원문 문서·웹페이지를 가리키는가?
2. 누가 언제 발행했고, 어느 페이지·표·섹션에 근거가 있는가?
3. 허용된 공식 자료 유형은 무엇이며 `fact_status`와 `verification_status`는 각각 무엇인가?
4. 링크를 눌러 독자가 원문을 확인할 수 있는가?
5. 서로 다른 자료가 충돌하거나 해석에 한계가 있을 때 그 상태가 표시됐는가?

## 자료 우선순위

1. 규제기관 공시·감사보고서·사업보고서
2. 회사 공식 IR·실적 발표·연차보고서와 제한 수집한 공식 IR PDF
3. 회사 공식 제품·사업·채용·보도자료·뉴스룸 웹페이지
4. 정부·규제기관 공식 원문
5. 비교사 공식 공시·IR·웹페이지
6. 신뢰할 수 있는 외부 분석 보고서(현재 canonical 런타임에서는 검색·입력하지 않음)
7. 원문 사실을 찾기 위한 언론 보도(현재 canonical 런타임에서는 검색·AI 선별하지 않음)

검색결과 요약, AI 요약, 재인용 블로그는 최종 출처로 쓰지 않는다. 가능한 경우 반드시 최초 발행 원문으로 교체한다.
현재 canonical 런타임은 보고서 결과에 실제 쓰이지 않는 외부 뉴스 검색·AI 선별을 생략한다.
따라서 외부 분석·언론은 공개 부록과 핵심 사실로 내보내지 않고, 1~8장은 자사 공시·IR·
회사 공식 홈페이지를 포함한 허용 공식 원문, 9장은 양사 공식 원문만 수록한다.

## 내부 주장 장부

본문을 쓰기 전에 다음 필드를 가진 주장 장부를 만든다. 이 장부는 검수용이며 완성 보고서 본문에는 노출하지 않는다.

`fact_id | 소유 장 | 주장 문장 | 대상 | 지표·사건 | 기간 | 값·상태 | source_id | 원문 위치 | 자료 유형 | fact_status | verification_status | evidence_binding | numeric_checks`

- `fact_id`는 `회사·대상 + 지표 또는 사건 + 기간·시점 + 값 또는 상태`로 만든다.
- 같은 `fact_id`가 두 장에 있으면 출력 전에 한 장만 소유자로 남긴다.
- 하나의 문장이 여러 사실을 포함하면 사실마다 원문 근거를 확인한다.
- 원문이 다른데 한 출처 번호로 뭉뚱그리지 않는다.
- 일반 `FactRecord.state_evidence` 계약은 그대로다. 공백을 정규화하고 casefold한 원문 조각의 SHA-256을 `Source.evidence_hashes`에 저장하며, 사실의 `state_evidence` 해시가 이 목록 안에 없으면 출처가 연결된 것으로 보지 않는다.
- `Source`의 URL·host·문서 ID·발행 주체·날짜·원문 해시와 공식 도메인 증명은 수집 시점의 서버 HMAC `provenance_seal`로 함께 잠근다. 저장된 보고서에서 이 값들을 고쳐 seal과 달라지거나 seal이 없으면 공식 원문으로 인정하지 않는다.
- 회사 공식 웹·IR처럼 공시가 아닌 공식 도메인은 동일 법인의 별도 DART·KIND 원문 또는 DART 기업개황의 `corp_code·corp_name·hm_url`에서 정확한 host를 독립 확인한다. 홈페이지 Source가 자기 자신의 공식성을 증명하거나, 보고서 조립 중 attester의 `evidence_hashes`를 추가해 맞추는 방식은 금지한다.
- 9장 후보용 DART 기업개황 `attestation_only` Source는 공개 사업 `FactRecord`나 양사 수치 근거가 아닌 **내부 provenance dependency**다. 직접 사실이 없어도 의존하는 공식 웹·HTML IR Source와 함께 내부 Report JSON·저장·감사 등록부에 남기고 `used_in=competitive_position`을 전파한다. 공개 웹·PDF·Notion·Markdown 부록에는 절대 표시하지 않으며 실제 후보 원문 citation만 공개한다.
- 9장 `comparison_basis` v1은 실제 1~8장 검증 사실을 역참조하는 저장 JSON/HMAC 형식의 읽기 호환이다. 재출고할 때 현재의 엄격한 경쟁 관계 문법으로 다시 검증하므로 과거 v1도 `GATE_STOPPED`될 수 있다. v2는 1~8장 의미 분류와 독립된 자사 공식 후보 한 문장·Source identity·위치·날짜·이중 해시·seal·attester를 잠근다. `evidence_sha256`은 공백 정규화+casefold 문자열, `evidence_exact_sha256`은 문장 추출 뒤 `strip`된 저장 문장 문자열 그대로의 UTF-8 SHA-256이다. exact 값은 원 HTTP 응답이나 PDF 파일 바이트 해시가 아니다. 두 값은 각각 `Source.evidence_hashes`와 `Source.exact_evidence_hashes`에 저장되고 두 목록 모두 HMAC seal에 결속한다. 일반 `FactRecord.state_evidence` 계약은 변경하지 않는다.
- 수치 사실은 원수치·나눗수·표시 자릿수·표시값을 담은 `numeric_checks`로 재현하고 최종 반올림은 `ROUND_HALF_UP`만 사용한다.

## 조사·검증 절차

### 1단계. 원문 식별

각 자료마다 다음을 기록한다.

`문서명 | 저자·애널리스트 | 실제 발행처 | 호스팅 기관 | 발행일 또는 확인일 | 페이지·표·섹션 | 원문 URL | 자료 유형`

- PDF는 PDF 자체의 표지·발행 정보와 실제 페이지를 확인한다.
- PDF에서 신뢰 가능한 문서 발행일 또는 보고기간을 결속하지 못하면 수집일을 사실 기준일로 대신 쓰지 않는다. 해당 PDF는 제한 수집·일반 citation으로만 보존하고 9장 비교사 후보 선정에서는 제외한다.
- 발행처는 URL 도메인이나 자료 저장 사이트가 아니라 PDF 표지·판권·머리글에 명시된 주체로 확정한다. KIND·DART·거래소·포털은 별도의 호스팅 기관으로 기록한다.
- 웹페이지는 페이지 제목·봉인된 machine-readable 발행일을 우선 사용한다. `corporate/about/product` 같은 안정 페이지에 발행일이 없을 때만 봉인된 수집일을 `확인 YYYY.MM.DD`로 쓸 수 있다. 보도·공지·archive·blog·문서형 URL은 확인일로 문서일을 대체하지 않는다.
- DART·KIND 등 공시는 접수번호 또는 문서 식별자가 남는 직접 링크를 사용한다.
- 서로 다른 URL은 원칙적으로 서로 다른 출처 번호다. 같은 허브의 여러 페이지를 한 행에 묶을 때는 각 페이지 이름과 링크가 모두 보여야 한다.
- 출처표는 잠긴 자료 등록부에서 생성하거나 그대로 복사한다. 작성 단계에서 문서명·발행처를 기억에 의존해 다시 입력하지 않는다.

### 2단계. 자료 유형 판정

- `공식 공시`: 법정 공시·감사자료
- `회사 공식 IR` 또는 `공식 IR`: 회사 실적 발표·투자자 자료
- `회사 공식 웹` 또는 `공식 웹`: 회사 제품·사업·채용·문화·보도자료
- `공식 파트너 자료` 또는 `파트너 공식 자료`: 현재 파트너가 직접 밝힌 관계와 역할
- `규제기관 공식 자료` 또는 `공식 규제기관 자료`: 정부·규제기관 원문
- `비교사 공식 공시`: 비교사의 공시 원문
- `외부 분석`: 증권사·전문 조사기관 분석
- `언론`: 원문 취재 보도

`공식`이라는 이유만으로 내용 전체가 실제 확정 사실인 것은 아니다. 자료 유형과 사실 상태를 따로 판정한다.
또한 런타임은 위 공식 유형을 닫힌 목록으로 판정한다. `NEWS` 종류이거나 허용 목록에
없는 표현은 문자열에 `공식`이 포함돼도 공개 핵심 사실의 근거가 아니다.

9장 후보용 공식 웹·HTML IR은 처음부터 끝까지 같은 정확한 host의 HTTPS여야 한다. HTTP
fallback·인증서 이름 대체 host·cross-host redirect는 허용하지 않는다. 안정적인
`corporate/about/product` 페이지는 명시 문서일이 없으면 봉인된 최신 수집일을 허용한다.
host·path·query의 `news/newsroom/press/media/notice/release/archive/blog`, 문서형 경로·키는
봉인된 machine-readable 문서일이 필수다. `search/results/find` 경로와 `q/s/query/keyword(s)/
search/term` key의 검색 결과는 최근 문서일이 있어도 항상 제외한다. 날짜가 잘못됐거나
미래이거나 보고서 `as_of_date` 기준 400일을 초과하면 후보와 canonical 직접 사실에서
제외한다. 캐시는 조회 당일 기준으로 이를 다시 검사하며 오래된 보고서는 적중시키지 않는다.
v2는 `시장점유율`을 경쟁 표지로 인정하지 않고
현재형의 명시적 경쟁 관계에서 후보가 실제 target/list slot일 때만 허용한다. 과거·
`former/potential`, 부정·제외, 인용·제3자 귀속, 협력·지원, 고객·공급사·파트너 경쟁,
모호한 별칭, `or/또는`는 거부한다. 이 닫힌 문법은 false-negative가 생길 수 있다.

공식 IR PDF는 robots.txt와 HTML 탐색 5쪽·링크 60개·PDF 최대 2개, 파일당 12 MiB·
80쪽·추출 12,000자·160조각, 사이트 전체 PDF 20 MiB·보존 12,000자 상한을 적용한다.
MIME `application/pdf`, `%PDF-` magic과 비암호화 문서를 확인하고, `pypdf 6.16.1`을
별도 프로세스에서 wall 10초·CPU 8초·메모리/주소공간 256 MiB(POSIX `RLIMIT_AS`,
Windows Job Object)·압축 해제 스트림 12 MiB·동시 워커 1로 실행한다. 앞 2쪽에서 대상
법인명·별칭을 확인하며 OCR 없이 추출 가능한 글자가 없거나 production에서 OS 자원 상한
설정이 실패하면 거부한다. 이 검사를 통과해도 현재 수집 경로에는 신뢰 가능한 문서
발행일·보고기간 결속이 없으므로 raw preflight·9장 후보·1~8장 canonical 선택 및 직접
사실로 허용하지 않는다.

### 3단계. 사실 상태와 검증 상태 판정

- `fact_status=actual`: 이미 발생했고 확정된 실적·계약·출시·운영 사실
- `fact_status=provisional`: 감사·확정 전 잠정 실적
- `fact_status=planned`: 미래 목표·일정·공식 계획
- `fact_status=estimated`: 외부 기관 또는 조사자가 계산·전망한 값
- `fact_status=scope_undisclosed`: 대상·금액·범위의 일부가 공개되지 않은 사실
- `verification_status=verified`: 원문·대상·시점·상태·근거 해시를 모두 대조함
- `verification_status=partial`: 일부 필수 범위만 확인됨
- `verification_status=insufficient`: 확정 본문 근거로 쓸 수 없음

`fact_status`와 `verification_status`는 서로 대체하지 않는다. `공식 자료`라고 자동으로
`actual·verified`가 되는 것도 아니다. 현재성은 `time_state=standing/current_issue/current_response`,
회계 재분류·일회성 영향은 `limitations`에 별도로 기록한다. 공개 본문에는
`verification_status=verified`인 사실만 들어갈 수 있다.

`estimated`는 런타임의 닫힌 열거값에는 포함되지만 현재 공개 가능한 `time_state` 조합이
없다. 따라서 외부 전망·조사자 추정은 내부 교차검증 기록에만 남기고 공개 본문과
부록에는 싣지 않는다.

### 4단계. 원문 대조

- 수치·단위·기간·연결/별도 범위를 원문과 대조한다.
- 표의 합계와 증감률을 직접 다시 계산하되, 계산값에는 `계산`임을 표시한다.
- 모든 표시 수치를 `numeric_checks`로 다시 계산하고 `ROUND_HALF_UP` 결과와 일치하는지 확인한다.
- `state_evidence`의 해시가 해당 `Source.evidence_hashes`에 실제로 등록됐는지 확인한다.
- 중요한 재무 수치는 가능하면 공시와 공식 IR 두 자료를 교차 확인한다.
- 경쟁사 비교는 자사와 비교사 양쪽 원문을 확인한다.
- 비교사 후보 문장은 자사 발행 주체(self-subject)의 한 원문 블록에서 후보 법인명이
  현재형의 명시적 경쟁 술어가 요구하는 실제 target/list slot에 있는 정확한 한 문장인지
  확인한다. 같은 문장에 법인명과 표지가 우연히 함께 있는 것만으로는 부족하다. v2의 두
  문장 해시는 Source의 두 해시 목록과 seal에 결속하고, 관계만 명시된 경우 고객·제품·
  시장 공통 범위는 양사의 별도 공식 원문으로 확인한다. 실제 비교 수치는 양사 DART의
  같은 완료 사업연도·회계 범위를 사용한다.
- 웹 링크는 최종 PDF 출력 직전에 열림 여부와 최종 이동 페이지를 확인한다.

### 5단계. 충돌 처리

- 같은 사실이 다르면 기간·연결 범위·발표 시점·재분류 여부를 먼저 확인한다.
- 원칙적으로 최신 공식 공시를 우선하되, 이전 발표와 달라진 이유가 해석에 중요하면 주장 옆에 설명한다.
- 충돌을 해결하지 못하면 수치를 본문에서 빼거나 `자료 간 불일치`를 명시한다.
- 임의 평균·추정으로 충돌을 숨기지 않는다.

### 6단계. 출처 번호 연결

- 번호는 본문 첫 등장 순서로 부여한다.
- 같은 원문 문서는 보고서 전체에서 같은 번호를 유지한다.
- 본문 번호와 부록 번호는 반드시 일치한다. PDF 생성기가 내부 링크를 지원하면 본문 번호에서 부록의 해당 행으로 이동하게 연결한다.
- 부록의 자료명은 클릭하면 원문으로 이동한다.
- 원문 URL 자체를 긴 문자열로 노출하지 않고 사람이 읽을 수 있는 자료명에 링크한다.

## 포함할 내용

- 본문에서 실제 사용한 일반 citation과 9장 후보 선정에 실제 사용한 후보 원문 citation만 수록. `attestation_only`를 포함한 내부 provenance dependency는 수록하지 않음
- 자료명·발행처·발행일 또는 확인일
- PDF 페이지·표·웹 섹션 등 구체적 위치
- 본문에서 사용한 장 또는 주장 범위
- 자료 유형과 사실 상태
- 직접 열 수 있는 원문 링크
- 해석에 필요한 잠정·계획·재분류·일회성 상태
- 공개 부록에는 후보로 실제 사용한 원문 citation만 수록한다. 후보 수집의 `failed·none·ok`, `candidate_scope_complete`, 상세 사유와 `attestation_only` Source는 내부 실행·감사 상태이므로 공개하지 않는다.

## 제외할 내용

- 본문에서 쓰지 않은 참고자료
- 검색결과·AI 요약·내부 메모·프롬프트
- `50개 보고서를 비교했다` 같은 제작 메타정보
- 에이전트 구성·검증 순서·작성 과정 설명
- 출처 없이 `다수 기사`, `업계 자료`, `회사 홈페이지`라고만 적은 행
- 열리지 않는 링크를 정상 출처처럼 표시한 행
- 긴 원문 URL을 셀 안에 그대로 노출한 형식
- 출처 번호만 있고 페이지·섹션 위치가 없는 문서

## 출력 형식

| 번호 | 자료·발행처 | 발행·확인일 | 원문 위치 | 본문 사용 | 자료·사실 상태 |
|---|---|---|---|---|---|
| [1] | 클릭 가능한 문서명 / 발행처 | YYYY.MM.DD | PDF p.00·표명 또는 웹 섹션 | 사용 장·주장 | 공식 공시 · 실제 |

### 열 작성 규칙

- `자료·발행처`: 공식 문서 제목을 임의로 바꾸지 않고, 발행처는 별도로 식별한다.
- `발행·확인일`: 문서 발행일을 우선한다. 날짜가 없는 웹페이지만 확인일을 쓴다.
- `원문 위치`: PDF는 실제 PDF 페이지, 웹은 섹션명·표명·문단 제목을 쓴다.
- `본문 사용`: `정체성·사업 모델`처럼 실제 사용 범위만 적는다.
- `자료·사실 상태`: 자료 유형, `fact_status`, `verification_status`를 서로 구분해 적는다.
- 같은 기준일을 본문의 여러 표에 반복하지 않는다. 시점 정보는 이 부록과 해당 장의 캡션 한 곳에서 관리한다.

## 중복 방지

- 같은 문서·URL은 출처표에 한 번만 등록한다.
- 하나의 출처가 여러 장에 쓰였으면 `본문 사용` 열에 장을 묶어 적는다.
- attester는 내부 Report JSON·저장·감사 등록부에만 한 번 보존한다. 공개 웹·PDF·Notion·Markdown 출처 목록에서는 완전히 숨기고 후보 원문 citation만 표시한다.
- 본문에 이미 있는 수치·사건을 부록에서 다시 설명하지 않고 사용 범위만 기록한다.
- 동일한 주의사항을 모든 출처 행에 반복하지 않는다. 문서 전체 공통 조건은 표 위에서 한 번 설명한다.
- 보고서 전체 기준일 문구는 출처 행에 반복하지 않는다. 다만 각 자료의 고유 발행일·확인일은 모든 행에 반드시 적는다.

## 시각화 조건

부록은 출처표만 사용한다. 그래프·플로우차트·출처 비율 도넛차트는 넣지 않는다. 출처 수가 많으면 표를 다음 페이지로 나누고 머리글을 반복한다.

상태는 텍스트로 구분한다. 여러 색의 배지나 신호등 색만으로 의미를 전달하지 않는다.

## 업종별 변형

| 업종 | 우선 원문 | 위치 표기 예시 |
|---|---|---|
| 상장사 공통 | 사업·분기보고서, 감사보고서, 공식 IR | 공시 접수번호, PDF 페이지·표명 |
| 제조·산업재 | 회사 공식 자료, 규제기관 등록·수주·설비 공시 | 등록번호, 공시 항목, 공장·제품 범위 |
| 플랫폼·SaaS | 공식 KPI 발표, 제품·요금 페이지 | 실적자료 표, 웹 섹션, 확인일 |
| 소비재·유통 | 점포·브랜드·유통 공식 페이지 | 지역·채널 표, 제품 페이지, 확인일 |
| 콘텐츠·IP | 회사 공식 자료, 공식 파트너의 투어·유통·라이선스 자료 | 자료명·집계기간, 작품·공연 범위 |

출처 유형만 달라질 뿐 `발행 주체·날짜·원문 위치·사실 상태·직접 링크` 필드는 모든 업종에서 유지한다.

## 근거가 부족할 때

- 원문 페이지를 찾지 못하면 해당 주장을 다시 조사하고, 끝내 확인할 수 없으면 본문에서 뺀다.
- 9장 후보 수집의 실제 `state`는 `failed·none·ok`뿐이다. 허용 범위를 끝까지 읽은 정상 완전 탐색의 `none`만 후보 없음이다. 접속·TLS·MIME·파서·카탈로그 실패는 `failed`, 상한 잘림은 별도 `truncated` state가 아니라 `candidate_scope_complete=False`와 상세 사유로 내부 감사 등록부에 남긴다. 불완전한 `failed`나 `ok`는 음성 결론이 아닌 `unknown`으로 처리한다.
- 공식 원문이 없고 외부 분석만 있으면 내부 실패 기록에만 남기고 공개 본문·부록에서 제외한다. 그 결과 필수 1~8장 계약 중 하나라도 부족하면 보고서 전체를 `GATE_STOPPED`로 끝낸다. 9장 비교만 성립하지 않으면 표준 부족 사유를 붙인 `Grade.PARTIAL` 기본 보고서로 출고한다.
- 웹페이지에 날짜가 없으면 확인일과 구체적 섹션명을 남긴다.
- 링크가 사라졌지만 규제기관 문서가 있으면 규제기관 원문으로 교체한다.
- 서로 다른 공식 자료가 충돌하면 최신 자료를 우선하고, 해석에 중요한 변경은 해당 주장 옆에 남긴다.
- 검증되지 않은 주장을 출처표에만 넣어 본문 신뢰를 보완하려 하지 않는다.
