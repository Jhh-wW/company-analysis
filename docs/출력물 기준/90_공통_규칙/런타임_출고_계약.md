# 런타임 출고 계약

- 상태: **현재 정본(Canonical)**
- 제품 키: `product:company-analysis`
- `Report.schema_version`: `company-report-v3-canonical`
- 캐시 스키마 토큰: `schema:company-report-v3-canonical`
- 적용 범위: 신규 조사, 데모 재생, 캐시 조회, 웹 표시, PDF·Notion 변환

이 문서는 출력 원칙을 프로그램이 매번 같은 방식으로 집행하기 위한 최소 계약이다. 프롬프트에 원칙을 적는 것만으로는 준수로 보지 않는다. 조사 결과가 구조화된 검사들을 모두 통과하고 최종 PDF까지 검수돼야 출고할 수 있다.

## 1. 입력과 서비스 경계

- 신규 분석 입력은 `회사명`과 선택적인 `주소 힌트`뿐이다.
- 지원 직무, 채용공고, 공고 이미지·OCR, 지원자 경험은 신규 조사 입력으로 받지 않는다.
- 직무별 업무·KPI·필수역량, 자기소개서·지원동기·면접 답안, 일반 준비 질문은 보고서에 만들지 않는다.
- `Report.job`, `requirements`, `guidance_lines`와 채용 결합 데이터는 구형 저장자료를 읽기 위한 호환 필드일 수 있으나 신규 보고서의 내용이나 화면을 구성할 수 없다.
- 회사 사실을 바탕으로 지원동기와 면접 답안을 구성하는 일은 독자가 직접 한다.

## 2. 고정 출력 구조

신규 보고서는 다음 순서를 한 번씩만 사용한다.

`핵심 요약 → 1 기업 정체성 → 2 사업 구조와 수익 모델 → 3 핵심 제품·서비스와 포트폴리오 역할 → 4 3개년 주요 변화와 실행 #과거 → 5 당면 과제와 대응 #현재 → 6 성장 전략 #미래 → 7 사업 운영과 파트너 구조 → 8 인재상과 일하는 방식 → 9 경쟁사 대비 핵심 경쟁력 → 부록 출처와 검증 상태`

- 1~9장은 모두 필수다. 핵심 요약은 1~8장 내부 초안에 9장을 결합한 뒤 마지막으로 작성하고, 요약까지 결합한 전체 객체가 최종 게이트를 통과한 뒤에만 첫 장에 표시한다.
- 10장은 없다. 9장 뒤에는 번호 없는 `부록. 출처와 검증 상태`만 둔다.
- 구형 키 `4-1`, `4-2`, `4-3`, `참고`, `附`, `활용`은 신규 출력 섹션으로 사용할 수 없다.
- 근거가 부족한 선택 하위 사실은 일반론으로 채우지 않는다. 그러나 필수 장이나 장별 최소 내용 계약이 하나라도 부족하면 부분 보고서·빈 장·구형 출력으로 대체하지 않고 보고서 전체를 `GATE_STOPPED`로 끝낸다.
- 공개 웹·PDF·Notion은 같은 승인 정본을 표현만 바꿔 렌더링한다. 출력 채널별로 질문·조언·추가 사실을 덧붙이지 않는다. 승인 전 결과는 관리자 전용 내부 `preview`로만 볼 수 있으며 공개 URL·다운로드·Notion 전송 대상이 아니다.
- 사용자 다운로드 정본은 PDF다. 구형 DOCX 다운로드는 활성 출력 계약에 포함하지 않는다.

내부 저장과 장 결합에는 아래 `section_id`만 이 순서로 사용한다. 부록과 핵심 요약은
`FactRecord.section_owner`가 아니며 숫자 장 번호도 내부 ID로 저장하지 않는다.

`identity → business_model → portfolio → past_changes → current_challenges → future_strategy → operations_partners → culture → competitive_position`

## 3. 구조화된 사실 원장

작성 전에 모든 후보 사실을 원장에 저장한다. 최소 필드는 다음과 같다.

| 필드 | 의미 |
|---|---|
| `fact_id` | 회사·대상·지표/사건·시점·값/상태를 정규화한 고유 ID |
| `claim` | 원문 범위를 넘지 않는 하나의 사실 주장 |
| `claim_type` | 장별 의미 역할을 나타내는 닫힌 영문 열거값 |
| `legal_entity` | 사실이 속한 정확한 법인 |
| `subject_scope` | 브랜드·제품·지역·관계의 원문 적용 범위 |
| `source_id` | 원문 출처 식별자 |
| `location` | 주장을 직접 뒷받침하는 원문 페이지·표·문단 |
| `as_of` | 기준일 또는 기간 |
| `time_state` | `completed`, `current_issue`, `current_response`, `future_plan`, `standing` 중 하나 |
| `section_owner` | 사실을 본문에서 한 번만 표시할 소유 섹션 |
| `fact_status` | `actual`, `provisional`, `planned`, `estimated`, `scope_undisclosed` |
| `verification_status` | `verified`, `partial`, `insufficient` |
| `state_evidence` | 수집 단계에서 원문 해시 등록부에 잠근 직접 근거 조각 |
| `source_date` | 원문 발행·공시·확인일. 사실 기준시점과 분리 |
| `evidence_support_terms` | 주장과 직접 근거 양쪽에 실제로 나타나는 핵심 근거어 |
| `evidence_binding` | 주장·근거·출처·위치·시점·구조 필드의 SHA-256 결속 |
| `raw_value` | 원문 원수치와 원단위. 공개 표시용 값으로 덮어쓰지 않음 |
| `calculation` | 단위 변환·비율 등 재현 가능한 산식 |
| `display_value` | 최종 공개 표시값 |
| `rounding_rule` | `ROUND_HALF_UP` 또는 수치가 아닐 때 `해당 없음` |
| `numeric_checks` | `원수치|나눗수|표시 자릿수|표시값`; `ROUND_HALF_UP` 결정론적 검산 |
| `fiscal_year` | 4장 완료 사업연도 실적의 실제 회계연도 |
| `event_date` | 4장 완료 실행이 실제 일어난 연도 또는 날짜 |
| `product_role`, `priority_signals` | 3장 대상의 사업 역할과 서로 다른 실제 우선 신호 |
| `basis_fact_ids` | 4장 변화 해석을 뒷받침하는 완료 실행·실적 사실 ID |
| `response_to_fact_id` | 5장 실제 대응이 직접 연결되는 미해결 문제 사실 ID |
| `limitations` | 잠정치·재분류·비공개·비교 한계 |
| `supports_causality`, `causal_subject`, `causal_mechanism`, `causal_outcome`, `causal_evidence` | 직접 인과를 쓸 때 필요한 허용 플래그와 주체·기제·결과·원문 근거 |
| `comparison_target`, `comparison_metric`, `comparison_definition`, `comparison_basis`, `comparison_period`, `comparison_scope` | 9장의 비교사·지표·정의/근거·기간·고객/제품/시장/회계 범위 |
| `comparator_source_id`, `comparator_state_evidence`, `comparator_evidence_support_terms` | 9장의 별도 비교사 공식 원문과 직접 근거 결속 |

- 출처 객체 `Source.evidence_hashes`에는 그 출처에서 실제로 수집한 원문 조각의 SHA-256만 둔다. `state_evidence` 해시가 이 목록에 없으면 해당 사실은 출처에 결속되지 않은 것이다.
- 수집 경계는 `Source`의 원문 URL·host·문서 ID·발행 주체·날짜·원문 해시·공식 도메인 증명을 서버 비밀키의 `provenance_seal`에 함께 결속한다. 보고서 조립·역직렬화·출고 검증 단계에서 입력값을 다시 seal해 주어서는 안 된다. seal이 없거나 한 필드라도 바뀌면 공식 원문으로 인정하지 않고 `GATE_STOPPED`한다.
- `기타` 종류의 회사 공식 웹·IR·파트너·규제기관 자료는 자기 선언만으로 공식 도메인이 되지 않는다. 같은 법인의 별도 DART·KIND 공식 공시 원문에 해당 host의 정확한 URL이 있고, 그 공시 Source 자체의 `provenance_seal`까지 유효할 때만 허용한다.
- 실제 배포는 32바이트 이상의 고정 `PROVENANCE_SEAL_SECRET`을 비밀 저장소에서 모든 worker에 동일하게 제공한다. 값이 없으면 프로세스 임시키를 사용하므로 재시작 뒤 기존 보고서는 안전하게 출고 차단된다.
- 3장 후보의 `subject_label`은 원문에 실제로 적힌 정확한 제품·서비스명이어야 하며 최종 사실의 대상 범위로 그대로 이어져야 한다.
- `fact_id`가 같은 사실은 본문 전체에서 한 번만 표현한다.
- 한 문장·표 행·도식 노드에는 같은 대상·시점·상태의 사실만 둔다.
- `verified`가 아니면 확정 문장으로 쓰지 않는다.
- 외부 분석의 해석은 회사의 공식 판단처럼 표시하지 않는다.
- 현재 단일-source 원장은 외부 보조근거의 역할을 별도로 표현하지 못하므로 모든 공개 `FactRecord`의 `Source.is_canonical_official`이 참이어야 한다. 뉴스·증권사·외부 분석은 메타데이터가 완전해도 공개 `FactRecord`·출처로 승격하지 않는다.

`Source.is_canonical_official`은 공백과 대소문자를 정규화한 뒤 아래
`SourceKind`·`source_type` 조합만 허용한다.

| `SourceKind` 값 | 허용 `source_type` |
|---|---|
| `공시` | `공식 공시`, `공식 재무 API`, `공식 공시·재무 API`, `공식 계획`, `규제기관 공식 자료`, `공식 규제기관 자료`, `비교사 공식 공시`, `비교사 공식 재무 API` |
| `기타` | `회사 공식 IR`, `공식 IR`, `회사 공식 웹`, `공식 웹`, `회사 공식 자료`, `공식 파트너 자료`, `파트너 공식 자료`, `규제기관 공식 자료`, `공식 규제기관 자료` |
| `뉴스` | 없음. 내부 교차검증 전용 |

장별 허용 `claim_type`은 다음과 같다.

| 장 | 허용값 |
|---|---|
| `identity` | `official_identity`, `operating_scope` |
| `business_model` | `revenue_model`, `customer_market`, `revenue_mix` |
| `portfolio` | `priority_product` |
| `past_changes` | `completed_execution`, `change_interpretation`, `historical_performance` |
| `current_challenges` | `current_issue`, `current_response` |
| `future_strategy` | `future_plan` |
| `operations_partners` | `operating_core`, `partner_role` |
| `culture` | `official_value`, `work_example` |
| `competitive_position` | `competitive_comparison`, `comparison_limitation` |

- 2장은 `revenue_model`과 `customer_market`을 모두 가져야 하며 각 고객·시장 사실의 `market_priority`가 비어 있으면 안 된다.
- 3장은 서로 다른 정확한 대상을 가진 `priority_product` 1~3개만 가져야 한다. 각 대상은 비어 있지 않은 `product_role`과 원문에서 각각 확인된 서로 다른 실제 `priority_signals` 2개 이상을 가져야 한다.
- 직접 인과 표현이 있거나 `supports_causality=true`이면 네 `causal_*` 필드가 모두 필요하고 `causal_evidence`가 결속된 `state_evidence` 안에 실제로 있어야 한다. 이 계약을 완곡한 표현으로 우회할 수 없다.

공식 자료 판정은 `source_type`에 `공식`이라는 글자가 있는지만 보지 않는다. 런타임의
닫힌 허용 목록과 `SourceKind` 조합이 맞아야 하며 `NEWS`는 항상 보조자료다.

장별 허용 `time_state`와 공개 가능한 `fact_status` 조합은 다음과 같다.

| 장 | `time_state` | 허용 `fact_status` |
|---|---|---|
| `identity`, `business_model`, `portfolio`, `operations_partners`, `culture`, `competitive_position` | `standing` | `actual`, `scope_undisclosed` |
| `past_changes` | `completed` | `actual`, `provisional` |
| `current_challenges` | `current_issue`, `current_response` | `actual`, `provisional` |
| `future_strategy` | `future_plan` | `planned` |

`estimated`는 닫힌 `fact_status` 열거값이지만 현재 공개 시간 상태와 결합할 수 없으므로
내부 조사·교차검증에만 남긴다. 공개 사실은 위 조합을 만족하면서
`verification_status=verified`여야 한다.

## 4. 시간 상태와 섹션 라우팅

| 상태 | 소유 섹션 | 출고 조건 |
|---|---|---|
| 최근 3년 내 완료된 실행과 확인된 결과 | 4장 `#과거` | 실행 시점과 결과 근거가 모두 있음 |
| 아직 해결되지 않은 문제 | 5장 `#현재` | 문제가 현재도 남았다는 최신 근거가 있음 |
| 현재 진행 중인 대응 | 5장 `#현재` | 회사가 실제로 착수했다는 근거가 있음 |
| 발표됐지만 아직 결과가 없는 계획 | 6장 `#미래` | 공식 계획·목표·예정 표현과 기준일이 있음 |
| 지속 중인 운영 기반·계약 관계 | 7장 | 관계 당사자·역할·유효 시점이 확인됨 |

- 계획을 완료 사실로, 오래된 사건을 현재 대응으로, 잠정치를 확정치로 바꾸면 출고를 중단한다.
- `가능하다`, `이어질 수 있다`, `영향을 준다` 같은 완곡 표현도 직접 인과 근거를 대신할 수 없다.
- 4장은 회사의 실제 결산월에 따른 비교 가능한 완료 `fiscal_year` 3개와, 기준일 이전 36개월의 `completed_execution`·`event_date`를 모두 가져야 한다. 모든 회사를 달력연도 12월 31일 결산으로 고정하지 않는다.
- 4장의 `change_interpretation`은 같은 장의 완료 실행·완료 실적 `basis_fact_ids`에 결속돼야 한다.
- 5장의 모든 `current_issue`에는 실제 `current_response`가 있어야 하고, 대응의 `response_to_fact_id`가 그 문제를 직접 가리켜야 한다.
- 4장의 공개 3개년 실적표는 행을 완료 사업연도, 열을 지표로 구성하고 표 위에 `단위: 억원`을 한 번만 표시한다. 셀에는 억원 표시값만 두며 원 단위 원값은 `FactRecord.raw_value`와 `numeric_checks`에만 보존한다.

## 5. 경쟁사 비교 계약

- 차별점마다 비교 대상과 선정 이유, 동일 비교축, 같은 고객·제품/서비스·시장·기간·정의·회계/사업 범위, 양사 근거, 확인된 차이, 비교 한계를 저장한다.
- 자사와 비교사 중 한쪽 공식 근거라도 없거나 고객·제품/서비스·시장·정의·기간·회계 범위가 다르면 공개 비교 행이나 순위·우위 문장을 만들지 않는다.
- 구조 차이만 확인되면 `운영 특성`으로 쓰고, 결과 우위까지 같은 조건으로 확인될 때만 `경쟁우위`로 쓴다.
- 기술력·브랜드·네트워크 같은 일반명사와 원문이 직접 뒷받침하지 않는 인과·수익성·고마진 표현은 금지한다.
- 검증 가능한 항목이 3개보다 적으면 개수를 억지로 맞추지 않는다.
- 유효 비교축은 단순한 매출·자산 규모 반복이 아니라 같은 기간·정의·연결/별도 범위에서 재현되는 영업이익률 등 사업 해석에 유효한 지표여야 한다. 규모 차이를 여러 계정으로 쪼개 차별점 수를 채우거나 규모 자체를 우위로 승격하지 않는다.
- 9장은 필수다. 양사 공식자료의 동일 고객·제품/서비스·시장·기간·정의·회계/사업 범위 비교가 하나도 성립하지 않으면 `비교 근거 부족` 문구를 공개하는 대신 보고서 전체를 `GATE_STOPPED`로 끝낸다.

## 6. 출고 게이트

실제 조립 순서는 `1~8장 내부 초안 → 9장 결합 → 1~9장으로 요약 생성 → 최종
build_published_report 게이트 1회`다. 1~8장 초안과 9장 결합 직후 객체는 저장·캐시·공개
렌더링할 수 없다. 다음 검사를 포함한 최종 게이트를 모두 통과해야 PDF를 생성·제공할
수 있다.

1. **범위 게이트**: 회사 중심 정보인지, 직무·개인 맞춤·투자 조언이 없는지 검사
2. **근거 게이트**: 모든 사실이 허용된 공식 원문과 연결되고 대상·시점·상태가 일치하는지 검사
3. **원자화 게이트**: 한 문장·표 행·도식 노드에 다른 상태의 사실이 섞이지 않았는지 검사
4. **소유권 게이트**: `fact_id` 중복과 같은 수치·사건·파트너 역할의 재서술 검사
5. **시간 게이트**: 4·5·6장의 `#과거·#현재·#미래` 라우팅 검사
6. **경쟁사 게이트**: 양사 근거, 비교 가능성, 차이와 한계 표시 검사
7. **편집 게이트**: 회사명만 바꿔도 성립하는 일반론, 제작 메타정보, 독자 행동 지침 검사
8. **장별 의미 게이트**: 1~9장 필수, 3장 제품 계약, 4장 회계연도·실행·해석 결속, 5장 문제–대응 결속 검사
9. **수치 게이트**: 원수치·산식·표시값과 `ROUND_HALF_UP` 재현 검사
10. **요약 게이트**: 요약이 실제 본문 `fact_ids` 부분집합과 독립 검증 결속에만 근거하는지 검사
11. **구조 게이트**: 고정 목차·순서, 표지, 핵심 요약, 출처 연결 검사
12. **PDF 시각·승인 게이트**: 모든 페이지 PNG와 동일 PDF 해시에 결속된 3인 역할별 승인 검사

구조 검사는 자동화할 수 있지만 시각 게이트를 텍스트 추출 검사로 대신할 수 없다.
사실·편집·시각은 서로 다른 세 검토자가 각각 승인한다. 사실 검토자는 최종 PDF의
전체 `fact_id`를 확인하고 실패 0건을 기록하며, 시각 검토자는 최종 PDF의 모든 페이지
PNG를 직접 확인한다. PDF와 각 페이지 PNG의 SHA-256은 모두 소문자 16진수 64자리
(`[0-9a-f]{64}`)여야 한다. 세 승인, 페이지 PNG 해시, 최종 PDF SHA-256은 같은 PDF 바이트에
결속한다. 본문·출처·레이아웃·PDF 해시가 바뀌면 기존 승인은 모두 무효다.
검수자 ID는 이메일 지문이 아니라 로그인 공급자의 불변 `sub`에서 서버가 만들며
`user:[0-9a-f]{20}` 형식만 받는다. PDF별 불변 참여자 원장은
`author·producer·fact·editorial·visual`의 완전한 역할 배정을 가져야 한다. 세 검수자는
서로 달라야 하고 작성자·생산자는 검수자가 될 수 없다. 원장이 없거나 설정과 다르면
승인을 저장하지 않는다.
세 역할 행과 최종 승인·출고 기록은 매번 재조립·재검산하고, 세 번째 승인부터 출고 기록
확정까지 하나의 DB transaction으로 처리한다. 공개 다운로드 때는 현재 후보 PDF·모든
페이지 PNG 해시, 승인 레코드, 결정론적 `record_sha256`, DB `release_sha256`을 다시 맞춘다.
텍스트 추출 결과만 믿지 않고 PDFium glyph 좌표의 중앙 본문 영역을 실제 PNG 픽셀과
대조한다. 헤더·쪽번호만 보이고 본문 glyph가 흰색·미렌더이면 prepare와 release 재검증
모두에서 출고를 차단하되, 중앙 제목이 실제로 보이는 성긴 표지는 허용한다.

## 7. 캐시와 구형 자료

- 캐시는 `product:company-analysis`와 `schema:company-report-v3-canonical`이 모두 맞고, 복원된 `Report.schema_version`도 `company-report-v3-canonical`일 때만 재사용한다.
- `schema:company-report-v2-specificity` 이하 자료는 신규 보고서 캐시 적중으로 인정하지 않는다.
- 구형 데모·저장 보고서는 마이그레이션하거나 새로 생성한다. 구형 섹션을 화면에서 새 목차처럼 이름만 바꾸는 방식은 허용하지 않는다.
- 캐시에서 읽은 보고서도 현재 출고 게이트를 다시 통과해야 한다.

## 8. 완료 판정

문서, 프롬프트, 코드, 데모 데이터, 캐시, 웹, PDF와 자동화 시험이 이 계약에 맞을 때만 “항상 이 원칙에 따라 출력한다”고 말할 수 있다. 한 경로라도 구형 구조를 출력하거나 게이트를 우회하면 전환은 미완료다.

구현 상태를 설명할 때는 `출고 계약`, `현재 코드로 확인된 구현`, `아직 시험하거나
구현하지 못한 제한`을 구분한다. 계약 문서에 적혀 있다는 이유만으로 실행 경로가
완료됐다고 보고하지 않는다.
