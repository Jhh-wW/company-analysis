> 챕터: 01. 역할 순서·회사 범위·구조화 사실 레코드 (본문 §1~§3)

## 1. 역할 순서

역할은 독립 에이전트나 하나의 프로그램 단계로 구현할 수 있다. 중요한 것은 순서와 입력·출력 계약이다.

1. **범위 설정자**: 회사명·법인·연결 범위·기준일을 확정한다.
2. **자료 수집자**: 자사 DART·공식 HTML IR·공식 웹 원문을 모은다. `NEWS_INTAKE`가 정확히 `"1"`이고 공식 근거 사전검사 뒤에도 빈 장이 남았을 때만 언론 보도를 보조 문서로 추가 수집한다. 공식 IR PDF는 제한 수집·인용하되 신뢰 가능한 문서 발행일 또는 보고기간을 결속하기 전에는 후보 원장에 넣지 않는다.
3. **섹션 조사자·사실 선택자**: 1~8장을 서로 독립적으로 조사해 구조화된 사실 묶음을 만든다. 선택 AI는 최대 2회이며 완결된 한 회차 결과만 채택한다.
4. **작가**: 한 문장에 하나의 원문 근거만 사용해 보고서 문체와 정보 순서를 정리한다.
5. **독립 Reviewer**: 원문과 앞뒤 공백 제외 완전일치하지 않는 새 문장을 작가와 대화·지시문을 공유하지 않고 대조한다. 명시적 실패 문장만 한 번 재작성하며, 재작성 완전일치는 코드로 확정하고 나머지만 새 Reviewer 재검사를 허용한다.
6. **총괄 분석자**: 검증된 1~8장을 공개 불가 내부 초안으로 조립하고 회사가 밝힌 차별점으로 9장을 결합한다. 출시 모드는 9장까지 갖춰야 하고, 동일 조건 양사 비교는 자료가 있을 때만 붙이는 선택 블록이다. 검증된 본문에서 핵심 요약을 결정론적으로 고른 뒤 최종 출고 게이트를 정확히 한 번 실행한다.
7. **중복 검토자**: 조판 전 원고에서 사실 소유권 위반과 같은 수치·사건의 재등장을 검사한다.
8. **레이아웃 작성자**: 정해진 UI 토큰으로 PDF를 만든다.
9. **사실·편집 자동검사**: 최종 객체의 모든 주장과 전체 `fact_id`를 잠긴 원장에 대조하고 인용·수치·중복·일반론·범위 밖 문구를 판정한다.
10. **PDF 전 페이지 자동검사**: 같은 PDF를 모든 페이지 PNG로 렌더해 구조·텍스트·glyph 가시성·페이지 해시를 판정한다.
11. **채널·해시 자동검사**: 웹·PDF·Notion이 같은 정본과 출고 레코드를 쓰는지 확인하고 검사 전후 보고서/PDF/페이지 지문을 다시 대조한다.

총괄 분석자는 앞 단계의 근거가 없는 내용을 새로 만들 수 없다. 작가와 레이아웃 작성자는 사실을 추가하거나 의미를 바꿀 수 없다. Reviewer 판정 누락·형식 파손과 두 번째 실패는 재시도하지 않고 해당 문장을 삭제한다.

검사 뒤 수정이 발생하면 새 작업 ID로 조립·PDF 렌더·자동검사를 다시 수행한다. 같은 작업 ID의 바뀐 hash를 조용히 재승인하지 않으며 조사·작성 기능이나 출력 채널은 어떤 이유로도 이 순서를 우회할 수 없다.

## 2. 회사 범위 확정

조사 전에 다음 값을 고정한다.

| 필드 | 기준 |
|---|---|
| 회사명 | 보고서 제목에 사용할 공식 명칭 |
| 분석 법인 | 본사·연결그룹·특정 자회사 중 하나 |
| 기준일 | 독자가 보고서를 읽는 정보 시점 |
| 실적 범위 | 연결/별도, 회계연도, 잠정/감사 완료 |
| 완료 재무 범위 | 회사의 실제 결산월에 따른 비교 가능한 최근 완료 사업연도 3개 |
| 완료 실행 범위 | 보고서 기준일 이전 36개월 |
| 비교군 | 내부 후보는 자사 DART 또는 DART 도메인 증명을 통과한 자사 공식 HTML IR·공식 웹이 현재형의 명시적 경쟁 관계 target/list slot에서 직접 지목한 1~3개사 또는 대체재. 발행일·보고기간을 결속하지 못한 공식 IR PDF는 후보에서 제외. 관계만 명시되면 고객·제품·시장 겹침은 별도 증명. 공개 비교 행은 공통 범위와 양사 DART 완료 사업연도 수치의 기간·정의·회계 범위가 모두 맞을 때만 채택 |

범위가 섞이면 수치 비교를 중단하고 먼저 법인·회계 기준을 통일한다.

## 3. 구조화 사실 레코드

모든 조사 결과는 아래 필드를 갖는다.

```text
fact_id: 회사·대상 + 지표 또는 사건 + 기간·시점 + 값 또는 상태
legal_entity: 사실이 적용되는 정확한 법인
subject_scope: 제품·모델·지역·관계의 원문 범위
relationship_or_action: 확인된 행동 또는 관계
claim: 보고서에 쓸 수 있는 사실 문장
claim_type: 장별 닫힌 영문 열거값(런타임 출고 계약의 허용표 참조)
section_owner: identity | business_model | portfolio | past_changes | current_challenges | future_strategy | operations_partners | culture | competitive_position
time_state: completed | current_issue | current_response | future_plan | standing
as_of: 기준일 또는 측정 기간
source_id: 원문 식별자
source_type: 공식 공시 | 공식 재무 API | 회사 공식 IR | 회사 공식 웹 | 공식 파트너 자료 | 규제기관 공식 자료 | 비교사 공식 공시
source_title: 원문 표지의 문서명
source_publisher: 원문 표지·머리글·판권의 실제 발행처
location: 페이지·표·문단
fact_status: actual | provisional | planned | estimated | scope_undisclosed
verification_status: verified | partial | insufficient
state_evidence: 해당 상태를 직접 확인하는 원문
source_date: 원문 발행·공시·확인일
evidence_support_terms: claim과 원문 근거 양쪽에 실제로 나타나는 핵심어
evidence_binding: claim·state_evidence·source_id·location·시점을 잠근 SHA-256
raw_value: 원수치와 원단위
calculation: 단위 변환·산식
display_value: 최종 표시값
rounding_rule: ROUND_HALF_UP 또는 해당 없음
numeric_checks: 원수치|나눗수|표시 자릿수|표시값
fiscal_year: 4장 완료 사업연도
event_date: 4장 completed_execution의 실제 사건 연도·날짜
product_role: 3장 제품·서비스의 사업 역할
priority_signals: 3장 원문에서 각각 확인된 서로 다른 실제 우선 신호 2개 이상
basis_fact_ids: 4장 변화 해석을 뒷받침하는 완료 실행·실적 ID
response_to_fact_id: 5장 대응이 직접 연결되는 미해결 문제 ID
limitations: 재분류·일회성·비교 한계 등(`limitation`은 구형 저장 호환용 별칭)
supports_causality: 직접 인과 근거가 있을 때만 true
causal_subject | causal_mechanism | causal_outcome | causal_evidence: 직접 인과의 주체·기제·결과·결속 원문
comparison_target | comparison_metric | comparison_definition | comparison_basis | comparison_period | comparison_scope: 9장 고객·제품/서비스·시장·기간·정의·회계 범위를 잠근 동일 조건 비교축
comparator_source_id | comparator_state_evidence | comparator_evidence_support_terms: 비교사 공식 원문 결속
```

실서비스 `comparison_basis`는 v1과 v2의 닫힌 JSON을 함께 읽는다.

- **v1 읽기 호환**은 실제 1~8장에 포함된 `verified` 후보 사실의 `fact_id·source_id`,
  DART `corp_code`, 공식 문서 ID, 단일 `state_evidence` 문장 정규화 SHA-256과 겹침 축을
  역참조한다. 저장 JSON/HMAC 형식만 호환하고 재출고할 때 현재의 엄격한 경쟁 관계 문법을
  다시 적용하므로 과거 v1도 `GATE_STOPPED`될 수 있다.
- **v2 독립 후보 원장**은 1~8장 의미 분류와 무관하게 자사 DART·공식 HTML IR·공식 웹
  Source의 정확한 한 문장을 보존한다. Source 종류·발행 주체·HTTPS host/URL·문서 ID·
  위치·날짜·문장·`evidence_sha256`·`evidence_exact_sha256`, 자사 DART 고유번호와
  attester를 함께 결속한다. 첫 해시는 공백 정규화+casefold 문자열, 둘째는 문장 추출 뒤
  `strip`된 저장 문장 문자열 그대로의 UTF-8 SHA-256이며 원 HTTP 응답·PDF 파일 바이트
  해시가 아니다. 두 값은 각각 `Source.evidence_hashes`와
  `Source.exact_evidence_hashes`에 있고 두 목록 모두 Source HMAC seal에 결속한다.

출고 게이트는 두 버전 모두에서 Source 등록부, 발행 법인(self-subject), 문서 ID·위치·
해시·seal을 다시 계산하고 후보 법인명이 현재형의 명시적 경쟁 술어의 실제 target/list
slot인지 검사한다. v2에서 `시장점유율`은 경쟁 표지가 아니며 과거·former·potential,
부정·제외, 인용·제3자 귀속, 협력·지원, 고객·공급사·파트너 경쟁, 모호한 별칭과
`or/또는`는 거부한다. 같은 문장+표지 조건만으로는 부족하고 엄격 문법의 false-negative를
허용한다. 순수 경쟁 문장을 1~8장 `claim_type`으로 위장하지 않는다. 일반
`FactRecord.state_evidence` 해시 계약은 v2 이중 해시 때문에 바뀌지 않는다.
`attestation_only` Source는 내부 Report JSON·저장·감사 등록부에만 보존하고 공개
웹·PDF·Notion·Markdown에는 실제 후보 원문 citation만 내보낸다.

시간 상태와 검증 상태는 위 영문 열거값으로 저장하고 표시용 한글은 렌더링 단계에서 붙인다.

출처 등록부의 각 `Source`는 실제로 수집한 원문 조각의 SHA-256 목록
`evidence_hashes`를 가진다. `state_evidence`의 해시가 이 목록에 포함되지 않으면 사실을
출처에 결속한 것으로 보지 않는다. 3장 후보의 `subject_label`은 원문에 실제로 적힌
정확한 대상명이어야 하며 최종 `subject_scope`와 의미가 달라지면 탈락한다.

필수 필드가 비어 있으면 본문 후보가 아니다. 같은 문장에 여러 법인·제품·상태가 들어가면 각 대상을 별도 `fact_id`로 나누고, 모든 상태와 근거가 같을 때만 출력 단계에서 묶는다.
모든 공개 `FactRecord`는 닫힌 공식 자료 허용 목록을 통과해야 한다. 핵심 사실은 공식 공시·IR·
회사 공식 홈페이지 근거로만 만들고, 언론 보도는 `FactRecord`가 아니라 공개 산문 인용과
출처 부록에만 쓰는 보조 문서로 남는다. `newspick` 기능 파일은 기존 호출 호환용으로만 남긴다.
