# 기능별 책임 지도

이 문서는 “무엇을 고칠 때 어느 폴더를 열어야 하는가?”에 답한다. 신규 회사분석의 내용·목차·출고 조건은 [보고서 구조](../REPORT_STRUCTURE.md)와 [런타임 출고 계약](../출력물%20기준/90_공통_규칙/런타임_출고_계약.md)이 우선한다.

## 정본 실행 흐름

```text
회사명·선택 주소 힌트
      │
      ▼
web ── 접근·요청·후보 확인
      │
      ▼
pipeline ── demo 또는 real 조사 조립
      │
      ├── 회사 식별·범위 확정
      ├── 공식 공시·IR·홈페이지 수집(뉴스 검색·AI 선별 생략)
      ├── 구조화 사실 원장 생성
      ├── 1~8장 작성
      ├── company_comparison으로 조건이 맞을 때만 양사 공식 근거 기반 9장 작성
      ├── report_summary로 검수 완료 본문 문장 3~5개를 결정론적으로 선택
      └── report_standard 출고 게이트
                         │
                         ▼
                 승인된 정본 보고서
                    ├── 웹 표시
                    ├── PDF 다운로드 정본
                    └── Notion 동등 렌더(설정 시)
```

`report_standard`와 필수 자동검사를 통과하지 않은 보고서는 저장된 초안이더라도 공개·다운로드할 수 없다. 출력 기능은 자동출고된 같은 보고서 객체를 렌더링할 뿐 사실·질문·조언을 추가하지 않는다.

## 접근·비용·입력

| 기능 | 책임 | 입력 → 출력 | 담당하지 않는 것 |
|---|---|---|---|
| `auth` | Google 로그인과 관리자 판정 | 인증코드·이메일·쿠키 → 세션·권한·CSRF 토큰 | 보고서 생성 |
| `sharelink` | 허용 사용자와 공유 링크 관리 | 이메일·공유키·DB → 접근 자격·열람 기록 | 보고서 내용 변경 |
| `budget` | 비용·속도·동시 실행 제한과 복구 | 실행 단계·비용 → 허용 여부·비용 원장 | 회사 사실 판정 |
| `business_candidate` | 회사명·주소 힌트로 정확한 회사 후보 제시 | 회사명·주소 → 검증 가능한 회사 후보 | 자동 확정·보고서 작성 |

신규 제품 입력은 회사명과 선택적인 주소 힌트뿐이다. `posting_image`와 채용공고 OCR은 구형 호환 코드이며 회사분석 신규 흐름에 연결하지 않는다.

| `revenuemix` | 공시의 제품·지역 매출 구성 정리 | 공시 본문 → 구성 행·기간 | 비공개 비율·이익 추정 |

| `company_specificity` | 회사 고유 근거와 일반론·거짓 관계 구분 | 사실 후보·회사 신원 → 채택·거절 근거 | 섹션 조판 |

## 보고서 작성·출고

| 기능 | 책임 | 입력 → 출력 | 담당하지 않는 것 |
|---|---|---|---|
| `spanselect` | 공식 후보와 연속 3개 완료 FY 표를 사전 확인한 뒤 장별 원문 범위를 선택. 완결된 1차를 즉시 채택하고 불완전할 때만 2차까지 실행 | 번호가 붙은 공식 원문 → 장별 상한 안의 SID 참조 완결 부분집합 | 뉴스 입력·회차 합집합·세 번째 호출·최종 문장 |
| `writer` | 원문 범위 안에서 읽기 쉬운 문장을 작성하고, 원문 완전일치가 아닌 문장은 별도 Reviewer로 검수. 명시적 실패만 한 번 재작성하며 완전일치는 코드로, 나머지는 새 Reviewer로 재검수 | 사실 후보·대상 장 → 검수 완료 문장 | 자료 수집·출력 파일 변환·검수 누락 문장 공개 |
| `provenance` | 출처 신원·위치·날짜·상태 관리 | 원문 조각 → 검증된 출처 등록부 | 원문 수집·새 사실 생성 |
| `company_comparison` | 자사와 비교사의 공식 근거를 같은 지표·기간·범위로 맞춰 조건부 9장 생성 | 공식 경쟁 관계·양사 공시 → 검증된 비교 또는 9장 생략 사유 | 한쪽 자료·업종 상식·외부 추정으로 비교사 지정 |
| `report_summary` | Writer 검수를 통과한 본문 `FactRecord` 문장 3~5개를 글자 변경 없이 결정론적으로 선택. 같은 장에서는 숫자 없는 문장을 우선하되 숫자 포함 문장뿐이면 그대로 허용 | 정본 장별 문장 → `verified_fact_reuse` 상태로 섹션에 결속된 핵심 요약 | AI 재작성·별도 요약 검수·본문 밖 사실·개인 조언 |
| `grading` | 자료 충족도와 부족 이유 판정 | 장·근거 → 등급·부족 상태 | 일반론으로 빈칸 채우기 |
| `report_standard` | 스키마·목차·사실 원장·소유권·시간·비교·범위 출고 게이트 | 보고서 초안 → 승인된 공개본 또는 차단 이유 | 조사·작성·레이아웃 |

`report_standard`는 `Report.schema_version=company-report-v4-canonical`만 승인한다. 같은 `fact_id`의 반복, 4·5·6장 시간 상태 오류, 한쪽 근거뿐인 공개 비교, 직무·개인 맞춤 내용 또는 구형 섹션이 있으면 출고를 차단한다. 유효 비교가 없어 9장을 생략한 1~8장 정본은 표준 부족 사유와 `Grade.PARTIAL`을 요구한다.

## 저장·운영·출력

| 기능 | 책임 | 입력 → 출력 | 담당하지 않는 것 |
|---|---|---|---|
| `storage` | 보고서·사실 원장·세션·캐시 저장과 조회 | DB·정본 스키마 → 저장·조회 결과 | 구형 캐시를 새 정본으로 승격 |
| `backup` | 실행 중 SQLite snapshot과 그 snapshot이 참조하는 불변 PDF를 한 recovery generation으로 봉인·재검증 | 영속 DB·artifact root → exact DB/PDF/manifest 세대 | 운영 외부 업로드·독립 서명·복구 전환·비밀값 백업(현재 BLOCKED) |
| `admin_dashboard` | 관리자 보고서·휴지통·주간 XLSX와 기간별 정기 작업 상태 관리 | 운영 DB·관리자 명령·cron claim → 대시보드 조회·XLSX·정리 결과 | 분석 실행·AI 호출·사용자 보고서 내용 변경 |
| `observability` | 단계·게이트·비용·시간·실패 이유 기록 | 실행 사건 → 감사 기록·지표 | 분석 실행·비용 차단 |
| `export_pdf` | 정본을 A4 PDF로 준비하고 report/PDF/page hash 결속 자동검사·자동출고 관리 | 정본 보고서 → 자동출고 PDF 또는 `GATE_STOPPED` | 사실 추가·수동 승인 우회 |
| `export_notion` | 같은 자동출고 정본을 Notion 블록으로 변환 | 자동출고 보고서·설정 → 페이지·URL | 별도 활용 질문·추가 분석 |
| `cost_tracking` | 단계별 내부 AI 변동원가와 고객 청구·서버 고정비 분리 | model/token/cache/batch/출고 → 비용 이벤트·청구 결정 | 가격 확정·결제 처리 |
| `pilot_evaluation` | 후보군 P01~P25를 보존하고 승인된 P01~P10의 고정 합격선을 평가 | 사용자·자동 판정 → 파일럿 요약 | 런타임 건별 승인·승인 밖 provider 실행 |
| `pipeline` | 식별부터 출고 게이트까지 기능을 순서대로 지휘 | 회사 입력·확인된 회사 → 정본 보고서 또는 중단 이유 | 각 기능의 세부 규칙 |

PDF는 사용자 다운로드 정본이다. PDF 생성 뒤 모든 페이지 렌더, 사실·인용·수치·구조,
채널 동등성과 검사 전후 hash를 자동검사한다. 모두 통과한 하나의 자동출고 레코드를
웹·PDF·Notion이 공유한다. 바이트가 바뀌거나 검사 하나가 실패하면 세 채널 전체를
차단한다. 구형 수동 승인 원장은 감사자료이고 DOCX 출력은 비활성이다.

## 실제 조사 엔진

`analysis_engine`은 `pipeline/real.py`가 사용하는 조사 실행 영역이다.

| 기능 | 정본 책임 |
|---|---|
| `name_match` | 사용자가 쓴 회사명을 정규화해 후보 검색 |
| `public_org` | 사업자번호로 공공기관 여부 확인 |
| `judgment` | 공식 자료 기준으로 분석 대상 승인·거절 |
| `cell_check` | 수집 결과의 최소 성립 조건 검사. 최종 v4 출고 승인은 `report_standard`가 소유 |
| `draft_check` | 작성 문장이 선택된 근거 범위를 벗어났는지 검사 |

`posting_gate`, `privacy_filter`, `fingerprint`는 채용공고 입력 시절의 구형 기능이다. 보존이 필요해도 신규 회사분석 파이프라인과 출력 계약에는 연결하지 않는다.

## 구형 호환 기능

- `posting_image`
- `posting_gate`, `privacy_filter`, `fingerprint`
- `Report.job`, `requirements`, `guidance_lines`
- `4-1·4-2·4-3·참고·附·활용` 섹션 키

이들은 이전 저장자료·시험을 읽는 호환 계층일 수는 있으나 신규 조사·캐시 적중·화면·PDF·Notion의 내용을 구성할 수 없다. 구형 데이터를 새 제목으로만 바꿔 출력하지 말고 v4 사실 원장과 섹션으로 명시적으로 마이그레이션하거나 새로 조사한다.

## 새 기능을 추가할 때

1. `features/<기능명>/` 안에 최소 로직과 시험을 함께 둔다.
2. 기능 전용 상수는 해당 기능이 소유하고 두 기능 이상에서 실제 공유할 때만 `core/`로 올린다.
3. 기능 내부에서 `web`을 가져오지 않는다.
4. 수집·작성 기능은 출고 게이트를 직접 우회하지 않는다.
5. 새 사실 필드는 사실 원장과 저장·캐시·모든 렌더러의 회귀 시험을 함께 갱신한다.
6. 새 출력 채널은 승인된 정본만 받아야 하며 채널 전용 내용을 추가하지 않는다.

구조를 선택한 이유와 예외는 [ADR 0001](../adr/0001-feature-oriented-structure.md)에 기록한다.
