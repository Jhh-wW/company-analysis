# 장기 휴면 백업·복구 안내

## 한 줄 결론

Render를 오래 꺼 두거나 삭제하기 전에는 **DB 백업 파일과 `.sha256` 파일을 함께
내려받아 검증한 뒤 암호화하고, 비공개 장소 두 곳에 보관**합니다. GitHub에는
프로그램 코드만 두고 DB 백업은 절대 올리지 않습니다.

비용 없이 오래 쉬는 기본 선택은 다음 두 벌이다.

1. DB와 체크섬을 암호화 압축한 뒤, 평소에도 로그인하는 개인 클라우드의 비공개 폴더
2. BitLocker 등으로 암호화한 USB 또는 외장 저장장치

개인 Google 계정은 2년 이상 활동이 없으면 계정과 자료가 삭제될 수 있습니다.
6개월 알림을 두고 클라우드의 암호화 파일을 내려받아 확인하며, 1년에 한 번 실제
복구를 연습합니다. [Google 비활성 계정 정책](https://support.google.com/accounts/answer/12418290)

## 무엇이 어디에 저장되나

Render 환경변수는 다음처럼 둡니다.

```text
STORAGE_DB_PATH=/var/data/storage.db
APP_DATA_ROOT=/var/data
```

- `/var/data/storage.db`: 보고서, 허용 사용자 이메일, 공유 링크, 비용·실행 기록
- `/var/data/logs`: DART·네이버 일일 사용량과 단계 로그
- `/var/data/analysis_engine`: 회사목록과 공시 원문 등 다시 받을 수 있는 수집 캐시
- Google·Anthropic·Notion·DART·Naver 비밀키: Render 환경변수에만 저장하며 DB 백업에 넣지 않음

환경변수를 설정하지 않은 로컬 실행은 예전 `app/data`, `analysis_engine/data`, `analysis_engine/logs` 위치를 그대로 사용합니다.

핵심 복구 자료는 `storage.db`입니다. 다만 이 백업 하나에는
`/var/data/observability/runs.jsonl`과 `/var/data/logs`의 상세 통계·단계 로그가
들어 있지 않습니다. DB만 복구해도 서비스 핵심 기능은 돌아오지만 과거 상세 통계는
사라질 수 있습니다. 그 기록도 필요하면 같은 날 별도 비공개 파일로 내려받아 함께
암호화합니다. 수집 캐시는 없어도 다시 만들 수 있습니다.

## 꼭 지킬 보안 규칙

`storage.db`에는 개인정보와 로그인 세션이 포함될 수 있습니다. 백업은 암호화되지 않은 원본 DB입니다.

- 공개 GitHub, 공개 링크, 메신저 공개방에 올리지 않기
- 개인용 암호화 저장소와 별도 장치처럼 서로 다른 두 곳에 보관하기
- DB와 같은 이름의 `.sha256` 파일도 함께 보관하기
- Render 디스크 속 백업은 디스크가 사라지면 같이 사라지므로 반드시 내려받기
- 비밀키는 DB와 함께 두지 말고 비밀번호 관리자에 따로 보관하기
- Windows에서는 이 도구가 파일 ACL을 소유자 전용으로 바꾸지 못하므로 BitLocker 등으로 보호되는 비공개 폴더에 즉시 옮기기

Render 영속 디스크 자체는 암호화되지만, 내 컴퓨터로 내려받은 파일은 별도로 보호해야 합니다. [Render 영속 디스크 공식 안내](https://render.com/docs/disks)

## 1. Render에서 안전한 백업 만들기

Render Dashboard에서 실행 중인 서비스의 **Shell**을 엽니다. Docker 안의 작업 폴더는 `/srv/app`이고, 명령은 다음과 같습니다.

```console
python tools/backup_sqlite.py backup
```

다음 두 파일이 `/var/data/backups`에 만들어집니다.

```text
storage-backup-날짜와시간.sqlite3
storage-backup-날짜와시간.sqlite3.sha256
```

이 명령은 실행 중인 SQLite 파일을 일반 복사하지 않습니다. SQLite 전용 Backup API로 한 시점의 완전한 DB를 만든 뒤, 체크섬과 DB 내부 상태를 검사합니다. 웹사이트가 켜져 있어도 백업할 수 있습니다.

내 컴퓨터에서 시험할 때만 프로젝트 최상위 폴더에서 다음 경로를 사용합니다.

```console
python app/tools/backup_sqlite.py backup
```

## 2. SCP로 내 컴퓨터에 내려받기

유료 Render 웹 서비스는 SSH와 SCP를 지원합니다. 먼저 Render 계정에 내 컴퓨터의 SSH 공개키를 등록합니다. 자세한 준비 방법은 [Render SSH 공식 안내](https://render.com/docs/ssh)를 따릅니다.

1. Dashboard에서 서비스 오른쪽 위 **Connect → SSH**를 엽니다.
2. 표시된 SSH 명령을 복사합니다. 실제 서비스 주소나 키는 문서·Git에 적지 않습니다.
3. 내 컴퓨터의 터미널에서 `ssh`를 `scp -s`로 바꾸고, 백업 화면에 나온 정확한 파일명을 넣습니다.

```console
scp -s YOUR_SERVICE@ssh.YOUR_REGION.render.com:/var/data/backups/정확한파일명.sqlite3 .
scp -s YOUR_SERVICE@ssh.YOUR_REGION.render.com:/var/data/backups/정확한파일명.sqlite3.sha256 .
```

`-s`는 Render가 권장하는 SFTP 방식입니다. 영속 디스크는 실행 중인 실제 서비스에서만 보이므로 임시·빌드·pre-deploy 인스턴스가 아니라 **실행 중인 서비스**에 연결해야 합니다. 전송 방식의 공식 예시는 [Render 디스크 문서의 Transferring files](https://render.com/docs/disks#transferring-files)에 있습니다.

SCP를 쓸 수 없을 때는 같은 공식 문서의 Magic-Wormhole 방법을 사용할 수 있습니다. Docker 이미지에는 기본 설치되어 있지 않으므로 Shell에서 설치가 가능한지 먼저 확인해야 합니다. 기본 방법은 SCP로 둡니다.

첫 배포가 끝나면 작은 실제 백업으로 **생성 → 내려받기 → 검증**을 반드시 한 번 시험합니다.

## 3. 내려받은 백업 확인

DB와 `.sha256`을 같은 폴더에 둡니다. 내 컴퓨터의 프로젝트 최상위 폴더에서 실행합니다.

```console
python app/tools/backup_sqlite.py verify "./storage-backup-날짜와시간.sqlite3"
```

`검증 통과`가 나와야 보관이 끝난 것입니다.

1. 옮기는 동안 파일이 바뀌거나 손상되지 않았는지 확인
2. SQLite 내부 표와 연결이 정상인지 확인

## 4. 검증한 두 파일을 암호화

`.sha256`은 암호화가 아니라 **파일이 망가지지 않았는지 확인하는 표식**입니다.
평문 `.sqlite3`를 그대로 클라우드에 올리지 않습니다.

Windows에서는 7-Zip 화면에서 두 파일을 함께 선택해 다음처럼 묶는 방법이 쉽습니다.

1. 압축 형식은 `7z`, 암호화 방식은 `AES-256`을 고릅니다.
2. **파일 이름 암호화**를 켜고 긴 암호를 입력합니다.
3. 암호는 백업 파일과 다른 비밀번호 관리자에 저장합니다.
4. 새 압축을 다른 임시 폴더에 한 번 풀고 `verify`를 다시 실행합니다.
5. 클라우드와 외장 저장장치에는 암호화된 `.7z`만 보관합니다.

두 보관 장소의 암호화 파일을 각각 복호화·검증하고, 최소 한 번은 실제 복구
연습까지 합니다. 평문 DB는 검증이 끝나면 클라우드 동기화 폴더에 남기지 않습니다.

## 5. 장기간 사용하지 않을 때

1. 새 백업을 만듭니다.
2. SCP로 DB와 `.sha256`을 내려받습니다.
3. `verify`를 실행한 뒤 두 파일을 암호화합니다.
4. 암호화 파일을 외부 비공개 장소 두 곳에 복사합니다.
5. 두 장소의 파일을 각각 복호화하고 `verify`로 검사합니다.
6. 비밀번호 관리자에 환경변수 **이름과 현재 값 또는 재발급 위치**를 보관합니다.
7. 아래 두 휴면 방법 중 하나를 선택합니다.

코드는 GitHub 외의 별도 비공개 압축본도 하나 보관하면 더 안전합니다. DB 백업은 공개 Git에 넣지 않습니다.
배포 이미지는 2030년까지 장기 지원되는 Debian 13(Trixie) 계열에 고정했습니다. 다만
Google·Notion·DART 같은 외부 서비스 규칙은 바뀔 수 있으므로, 오래 쉬었다가 복구할
때는 아래 GitHub 자동검사를 먼저 통과시켜야 합니다.
[Debian 13 지원 안내](https://www.debian.org/releases/trixie/)

### 짧게 쉬고 빨리 다시 쓸 때

Render 서비스를 정지·Suspend하고 디스크를 유지합니다. 다시 켜기는 쉽지만, **정지 상태의 디스크 비용까지 0원이라고 가정하면 안 됩니다.** 그때의 Render 요금과 Billing 화면을 직접 확인합니다.

### 오래 쉬며 앞으로 나갈 돈을 0원으로 만들 때

백업 두 벌의 검증과 복구 연습이 끝난 뒤 다음을 모두 확인합니다.

1. Render 유료 웹 서비스 삭제
2. 붙어 있던 영속 디스크도 삭제됐는지 확인
3. Dashboard의 **Billing**에서 남은 유료 리소스가 0개인지 확인

삭제하면 Render 안의 자료는 되돌리기 어렵습니다. 외부 백업 검증 전에는 삭제하지 않습니다. 이미 이번 달에 사용한 금액과 별도 도메인 등록비는 사라지지 않습니다. [Render Dashboard의 Billing 공식 안내](https://render.com/docs/render-dashboard#manage-billing)

## 6. 나중에 새 Render 디스크로 복구

복구 도구는 기존 DB를 절대 덮어쓰지 않습니다. 서버가 정말 멈췄는지 프로그램이 완벽히 확인할 수 없기 때문에, 항상 **새 파일명**에 복구한 뒤 환경변수를 그 파일로 바꿉니다. 기존 DB가 손상됐어도 그대로 남습니다.

먼저 암호화 백업을 비공개 임시 폴더에 복호화하고, 내 컴퓨터에서 다시 `verify`합니다.
그다음 **업로드보다 먼저** Render의 Maintenance Mode를 켜고, 진행 중인 보고서
작업이 끝났는지 확인합니다. 새 빈 서비스에서도 같은 순서를 권장합니다.
Maintenance Mode를 켜도 SSH는 유지됩니다.

그 후 Render Dashboard의 실행 중 서비스 Shell에서 업로드 폴더를 만듭니다.

```console
mkdir -p /var/data/restore
```

내 컴퓨터 터미널에서 두 파일을 새 Render 디스크로 올립니다.

```console
scp -s 정확한파일명.sqlite3 YOUR_SERVICE@ssh.YOUR_REGION.render.com:/var/data/restore/
scp -s 정확한파일명.sqlite3.sha256 YOUR_SERVICE@ssh.YOUR_REGION.render.com:/var/data/restore/
```

Render Shell에서 **아직 존재하지 않는 새 DB 이름**으로 복구합니다.

```console
python tools/backup_sqlite.py restore /var/data/restore/정확한파일명.sqlite3 --target /var/data/storage-restored-날짜.db
```

대상 파일이 이미 있으면 도구가 중단됩니다. 다른 새 이름을 사용해야 하며, 기존 파일을 지우거나 덮어쓰는 선택지는 제공하지 않습니다.

복구가 끝나면 다음 순서로 전환합니다.

1. 복구 중에는 `PIPELINE=demo`, `BETA_ADMIN_ONLY=1`로 둡니다.
2. 저장소 루트 `render.yaml`의 `STORAGE_DB_PATH`를
   `/var/data/storage-restored-날짜.db`로 바꿉니다. Dashboard에서만 바꾸면 다음
   Blueprint 동기화 때 옛 경로로 돌아갈 수 있습니다.
3. 이 변경을 비공개 GitHub에 올리고 Actions의 `tests`와 `container-smoke`가 모두
   초록색인지 확인한 뒤 배포합니다.
4. 새 Render 주소가 생겼다면 Google의 승인된 리디렉션 URI와 Render의
   `GOOGLE_REDIRECT_URI`를 새 주소로 함께 바꿉니다.
5. Render Shell에서 업로드한 원본 백업을 다시 `verify`하고, 복구 완료 메시지·배포
   로그·`/healthz`가 정상인지 봅니다.
6. 전부 정상이면 Maintenance Mode를 끕니다.
7. 아래 기능 확인 목록을 바로 실행합니다. 문제가 있으면 Maintenance Mode를 다시 켭니다.
8. 예전 DB와 로컬 평문 복호화 파일은 확인이 끝날 때까지 비공개로 두고, 끝나면
   필요한 보존본 외에는 안전하게 정리합니다.

Maintenance Mode는 유료 웹 서비스에서 공개 요청을 `503`으로 막으면서 SSH는 유지합니다. [Render Maintenance Mode 공식 안내](https://render.com/docs/maintenance-mode)

## 권장 주기

- 사용 중: 최소 월 1회
- 큰 코드 변경·배포 전: 매번 1회
- Render를 정지·삭제하기 전: 마지막 1회
- 장기 보관 중: 6개월마다 체크섬 검사, 1년에 한 번 복구 연습

체크섬은 파일 손상만 알려 줍니다. 계정 분실이나 저장장치 삭제를 막아 주지는 않으므로 반드시 서로 다른 두 장소에 보관해야 합니다.
