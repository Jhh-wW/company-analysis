# 기업분석2 배포·운영·복구 런북

작성 기준일: 2026-08-22
적용 대상: 단일 인스턴스·단일 SQLite 운영 구성
원칙: 운영 DB를 직접 덮어쓰거나 삭제하지 않는다. 모든 복구 검증은 임시 복사본에서만 수행한다.

## 1. 역할과 배포 차단선

- 배포 책임자: maintenance 전환, preflight 판정, 배포 시작·중단 결정
- 데이터 책임자: 독립 체크섬 보관, 백업 다운로드, 임시 복구 검증
- 확인자: 결과 JSON과 플랫폼 로그를 교차 확인하고 시간·담당자를 변경 기록에 남김
- P0 또는 배포 차단 P1이 열려 있거나, 아래 명령 중 하나라도 종료 코드가 0이 아니면 배포하지 않는다.
- 이 런북은 명령을 설명할 뿐 자동 push·배포·외부 호출을 수행하지 않는다.

`ops/release_readiness.py`는 표준 라이브러리만 사용한다. 현재 컨테이너 이미지는 `ops/`를 복사하지 않으므로, 운영 DB preflight를 쓰려면 먼저 이 파일을 이미지에 명시적으로 포함하거나 운영 DB를 읽기 전용으로 마운트한 승인된 관리 실행 환경을 마련해야 한다. 이 조건이 없으면 live preflight는 미실행으로 간주한다.

종료 코드 의미:

- `0`: 해당 검증 통과
- `1`: 입력·무결성·실행 오류
- `2`: preflight 배포 차단 항목 존재

## 2. 장애 유형별 대응과 RPO/RTO 제안값

아래 값은 현재의 일일 백업·1 GB 단일 디스크·단일 인스턴스를 전제로 한 **초기 제안값**이며 SLA 확정값이 아니다. 첫 복구 훈련에서 실제 시간을 재고 승인된 값으로 바꾼다.

- RPO: 장애 시점에서 허용할 수 있는 데이터 손실 시간
- RTO: 탐지 후 사용자 기능을 안전하게 정상화할 때까지의 시간
- `B`: 마지막으로 독립 체크섬과 임시 복구까지 통과한 백업의 나이
- `T_volume`: 새 영속 디스크/인스턴스 준비에 플랫폼이 실제로 걸린 시간
- `T_provider`: 외부 공급자의 과금·상태 확인 응답 시간

| 장애 유형 | 탐지 | 격리 | 복구 | 검증 | 회고 | RPO 제안 | RTO 제안 |
|---|---|---|---|---|---|---|---|
| DB 손상·외래 키 오류 | `/readyz`, 시작 실패, `preflight`의 integrity/FK 실패, 백업 검증 실패 | 즉시 maintenance, 새 admission 차단, DB/WAL/SHM을 건드리지 않고 읽기·배포 중단 | 독립 해시가 맞는 최신 백업을 **새 DB/새 디스크**에 복구. 기존 운영 DB 제자리 덮어쓰기 금지 | 독립 해시 3자 대조, 임시 복구, 새 대상 preflight, 레코드 수·중요 상태 확인, 무비용 demo | 최초 오류 시각·직전 변경·손상 범위·마지막 정상 백업·재발 방지 소유자를 incident에 기록 | `min(B, 24시간)` 목표. 실제 RPO는 검증된 백업 나이 `B` | 120분 + `T_volume` 제안 |

| 운영 키·토큰 노출 의심 | 비밀 스캔/플랫폼 경보, 인증 실패 급증, 예기치 않은 내부 trigger, 서명 검증 이상 | 영향 secret을 플랫폼에서 폐기·교체하고 관련 내부 경로/real pipeline 차단. 값 자체를 로그나 incident에 기록하지 않음 | backup/maintenance trigger와 공급자 자격증명을 각각 최소 권한으로 회전. provenance seal 키는 과거 검증 연속성을 보존하는 버전 관리·승인 계획 뒤 회전 | 이전 자격증명 거부, 새 자격증명 최소 기능만 성공, 유료 호출은 별도 승인된 무비용/fake 시험으로 대체, seal 검증 범위 확인 | 노출 원인·접근자·사용 흔적·회전 목록·과거 seal 영향·재발 방지를 기록 | DB 데이터 0 손실 목표. 과거 seal 검증 연속성은 별도 보존 요구 | 내부 trigger 30분, 공급자/플랫폼 회전은 120분 + 외부 처리시간 제안 |

모든 유형의 incident에는 탐지 시각, maintenance 시각, 마지막 정상 상태, 사용한 백업 세대와 **독립 해시의 보관 위치 식별자**, 격리·복구·검증 담당자, 실제 RPO/RTO, 남은 위험과 후속 기한을 남긴다. 비밀 값, 공유 링크 원문, 세션 토큰, 개인 식별 원문은 기록하지 않는다.

## 3. 백업 무결성과 독립 서명 manifest

같은 S3 위치의 `.sqlite3`와 `.sha256`은 전송 손상 탐지에는 유효하지만 독립적인 진본성 근거는 아니다. 실제 `s3.run_backup`은 S3 client 생성 전에 production-ready `BackupManifestAppender` 주입을 요구하고, 재다운로드 검증 뒤 다음 값을 DB/sidecar와 다른 권한·보존 경계의 서명 append-only 원장에 조건부 append하고 head를 다시 읽어 검증해야만 성공을 반환한다.

- 정확한 저장 공급자, bucket, DB object key, sidecar object key
- DB 파일명·SHA-256·크기와 sidecar 객체 SHA-256
- 데이터 경계/권한 ID와 서로 다른 manifest 경계/권한 ID
- 단조 증가 sequence, 이전 레코드 hash, 생성/보존 시각, 서명 key ID·서명

성공 응답과 cron 로그는 `manifest_backup_id`, `manifest_sequence`, `manifest_record_sha256`을 남긴다. 이 세 값의 최신 checkpoint는 S3와 다른 접근 통제의 append-only 운영 로그에 보존한다. 복구 때 DB나 sidecar에서 값을 다시 계산해 checkpoint로 쓰면 안 된다.

### 3.1 현재 외부 설정 차단 상태

저장소에는 운영 `BackupManifestAppender` 구현과 설치 호출이 없다. 따라서 다음을 실제 인프라에 구성·검증하기 전 정기 백업과 복구 gate는 의도적으로 **BLOCKED**다.

1. DB bucket 쓰기 주체와 다른 권한 주체의 WORM/object-lock/append-only manifest sink
2. sink retention 35일 이상과 조건부 append(CAS)·전체 chain/head read-back
3. 32바이트 이상 서명 키의 secret-manager 주입과 key ID·회전·과거 검증 정책
4. 앱 시작 시 `install_manifest_appender_provider(...)` 단일 설치
5. 최신 `manifest_sequence` checkpoint를 복구 실행기에 주입하는 별도 통제 경로
6. 실제 adapter 장애·재시작·동시 append·복구 훈련 증거

로컬 `LocalAppendOnlyManifestSink`는 공격 단위시험 전용이며 `production_ready=False`라 운영 백업 성공에 사용할 수 없다.

### 3.2 백업 검증

1. 대상 백업의 생성 시각, 정확한 bucket/object key, 최신 독립 checkpoint를 변경 기록에 적는다.
2. DB와 같은 이름의 `.sha256` 한 쌍을 암호화된 격리 작업 경로에 받는다.
3. 승인된 운영 adapter가 `IndependentManifestGate`를 `release_readiness.main(..., manifest_gate=gate)`에 주입해 다음 인자를 실행한다. `ops/release_readiness.py`를 직접 실행하면 sink/signer가 없으므로 종료 코드 1로 닫히는 것이 정상이다.

```text
python -m <승인된_manifest_adapter_wrapper> verify-backup \
  --database <backup.sqlite3> \
  --checksum <backup.sqlite3.sha256> \
  --expected-sha256 <호환_검사용_DB_SHA256> \
  --manifest-backup-id <독립_로그의_backup_id> \
  --manifest-storage-bucket <정확한_bucket> \
  --manifest-object-key <정확한_DB_object_key> \
  --manifest-checksum-key <정확한_sidecar_object_key> \
  --data-boundary-id <DB_권한경계_ID> \
  --data-authority-id <DB_쓰기주체_ID> \
  --manifest-min-sequence <독립_로그의_최신_sequence>
```

`--expected-sha256`과 sidecar는 호환·전송 검사용일 뿐 독립 근거가 아니다. 통과 조건은 독립 sink의 전체 서명 chain과 최신 scope head, 외부 checkpoint sequence, 원격 객체 identity, DB/sidecar 실제 지문, `integrity_check`, 외래 키, 필수 스키마가 모두 맞는 것이다. 결과에는 레코드 내용이나 자격증명이 출력되지 않는다.

manifest append가 실패하면 백업 성공은 반환하지 않는다. append 성공·read-back 실패를 구분할 수 없는 경우 이미 검증된 S3 쌍은 manifest가 가리킬 가능성이 있어 자동 삭제하지 않고 미확정 객체로 보존한다. 재시도 전에 운영자가 독립 원장과 정확한 object key를 대조해 reconcile해야 하며, 미확정 쌍의 개수·총바이트 경보와 승인된 유한 보존 정책이 없으면 반복 재시도를 중단한다.

## 4. 임시 복사본 복구 dry-run

앱 이미지의 `python tools/backup_sqlite.py restore`와 공개 `restore_backup()`은 독립
manifest gate 우회를 막기 위해 항상 fail-closed한다. sidecar, expected hash, 로컬 receipt
파일, CLI flag는 공격자가 DB와 함께 다시 만들 수 있어 승인 증거로 받지 않는다. 운영 새
DB 게시는 production sink/signer와 최신 checkpoint를 주입한 승인 adapter wrapper 안에서만
구현한다.

복구 dry-run은 운영 DB 경로를 대상으로 실행하지 않는다. `--temp-parent`는 비어 있는 격리 작업 디스크의 상위 디렉터리만 지정한다. 도구는 그 아래에 무작위 임시 디렉터리를 만들고 SQLite Backup API로 새 파일을 만든 뒤 스키마·전체 테이블별 레코드 수를 비교하고 자동 삭제한다.

```text
python -m <승인된_manifest_adapter_wrapper> restore-dry-run \
  --database <backup.sqlite3> \
  --checksum <backup.sqlite3.sha256> \
  --expected-sha256 <호환_검사용_DB_SHA256> \
  --manifest-backup-id <독립_로그의_backup_id> \
  --manifest-storage-bucket <정확한_bucket> \
  --manifest-object-key <정확한_DB_object_key> \
  --manifest-checksum-key <정확한_sidecar_object_key> \
  --data-boundary-id <DB_권한경계_ID> \
  --data-authority-id <DB_쓰기주체_ID> \
  --manifest-min-sequence <독립_로그의_최신_sequence> \
  --temp-parent <격리된_임시_상위_디렉터리>
```

통과 후 다음을 확인한다.

- 출력 상태가 `임시 복구 통과`이고 종료 코드가 0이다.
- 지정한 상위 디렉터리에 `release-restore-dry-run-*` 잔여물이 없다.
- 원본 백업 파일의 해시는 실행 전후 동일하다.
- manifest 경계/권한 ID, 최신 checkpoint의 출처와 검증 시각을 변경 기록에 남겼다.

실패 시 파일을 손으로 고치거나 sidecar를 재생성하지 않는다. 다른 세대의 백업을 같은 절차로 검증하고, 실패한 객체는 보존한 채 사고 조사 대상으로 표시한다.

## 5. 고아 작업·DB·디스크 preflight

### 5.1 maintenance와 admission 차단

1. 관리자 `/admin/settings`에서 서비스를 `maintenance`로 바꾼다.
2. 원인, 사용자 영향, 다음 조치를 모두 입력한다. 빈 설명으로 전환하지 않는다.
3. 새 조사 admission이 거절되는지 확인한다.
4. 기존 작업이 자연 종료할 시간을 준 뒤 아래 명령을 실행한다.

```text
python ops/release_readiness.py preflight \
  --database /var/data/storage.db \
  --data-root /var/data \
  --require-maintenance
```

기본 배포 차단 기준은 다음과 같다.

- 미정산 비용 예약, 진행 중 공유 링크·관측·회원·운영·Notion 작업 중 하나라도 1건 이상
- maintenance가 아님
- 공유 링크 열람 이벤트 100,000건 초과
- 디스크 여유 256 MiB 미만 또는 사용률 85% 초과
- DB 768 MiB 초과 또는 WAL 128 MiB 초과
- SQLite 무결성·외래 키·필수 스키마 오류

임계값은 1 GB 영속 디스크의 안전 여유를 위한 초기값이다. 다른 디스크 크기를 쓰면 변경 승인서에 근거를 남기고 명령 옵션으로 명시한다. 단순히 통과시키려고 임계값을 올리지 않는다.

`작업 중단 표식`은 경고다. 1건 이상이면 ID나 원문 데이터를 도구로 출력하지 말고 기존 관리자 화면·보호된 로그에서 원인과 재기동 복구 결과를 확인한다.

### 5.2 고아 상태 처리

- `budget_spend_inflight`를 직접 삭제하지 않는다. 과금 여부가 불명확하면 원장이 해당 capability를 fail-closed로 막는 상태를 유지한다.
- `running`, `pending`, `reserved`, `in_progress` 행을 SQL로 임의 변경하지 않는다.
- 재기동 복구가 `interrupted` 또는 비용 미확정으로 마감한 결과를 먼저 확인한다.
- 업무 책임자가 공급자 청구·관측 기록·보고서 저장 여부를 대조해 정산 또는 재시도 여부를 결정한다.
- DB 파일, WAL, SHM을 실행 중 복사·삭제·이동하지 않는다.

## 6. graceful drain과 배포 순서

현재 플랫폼 종료 유예는 300초이고 앱의 정상 drain 대기는 240초다. 이 60초 여유 안에 취소·중단 표식 기록·프로세스 종료가 끝나야 한다.

1. maintenance 전환과 preflight 통과를 먼저 완료한다.
2. 독립 체크섬을 사용한 최신 백업 `verify-backup`과 `restore-dry-run` 통과를 확인한다.
3. 플랫폼에서 수동 배포를 시작한다. 자동 배포는 사용하지 않는다.
4. SIGTERM 뒤 로그에서 새 admission이 닫히고 실행 중 작업 대기 수가 감소하는지 확인한다.
5. 240초를 넘긴 작업은 취소 전에 `job_interruptions`에 기록되고 비용 미확정으로 마감되는지 확인한다.
6. 300초 강제 종료가 발생하거나 중단 표식 저장 오류가 있으면 배포를 실패로 판정한다.

## 7. 기동 후 확인과 maintenance 해제

1. `/readyz`가 성공하기 전 트래픽을 정상으로 돌리지 않는다.
2. 컨테이너가 비-root 단일 worker이고, DB 경로가 영속 디스크 아래인지 확인한다.
3. 새 버전에서 preflight를 다시 실행한다. 진행 중 집계가 모두 0이고 SQLite 검사가 통과해야 한다.
4. 비용 원장 미확정, 관측 pending/running, 공유 링크 running/awaiting_release가 없는지 확인한다.
5. 짧은 무비용 demo 확인 뒤에만 관리자 화면에서 `normal`로 되돌린다.
6. 정상화 시각, 확인자, readiness 결과를 변경 기록에 남긴다.

## 8. 롤백과 복구

- 코드 롤백도 먼저 maintenance와 graceful drain을 거친다.
- 데이터 복구가 필요하면 검증된 백업으로 **새 DB 파일 또는 새 영속 디스크**를 만든다. 운영 DB를 제자리 덮어쓰지 않는다.
- 새 복구 대상에서 `restore-dry-run`과 동일한 무결성·행 수 검사를 통과한 뒤 경로 전환을 별도 승인한다.
- 전환 실패 시 기존 운영 DB를 보존하고 경로만 되돌린다.
- 복구 후 첫 외부 백업이 생성되고 독립 체크섬 검증까지 끝나기 전 incident를 닫지 않는다.

## 9. 금지 사항

- 운영 DB·WAL·SHM 직접 삭제 또는 덮어쓰기
- 같은 저장소에서 함께 받은 DB와 sidecar만으로 진본성 확정
- 독립 해시를 DB에서 다시 계산하거나 sidecar 값으로 대체
- maintenance 없이 배포, preflight 종료 코드 무시
- 고아 행 수동 삭제로 차단 우회
- 로그에 공유 링크 원문, 세션 토큰, API 키, 개인정보 출력
- 이 절차를 이용한 push, 외부 배포, 유료 API 호출
