# 기업분석2 배포·운영·복구 런북

작성 기준일: 2026-08-22
적용 대상: 단일 인스턴스·단일 SQLite 운영 구성
원칙: 운영 DB를 직접 덮어쓰거나 삭제하지 않는다. 모든 복구 검증은 임시 복사본에서만 수행한다.

## 1. 역할과 배포 차단선

- 배포 책임자: maintenance 전환, preflight 판정, 배포 시작·중단 결정
- 데이터 책임자: 독립 체크섬 보관, 백업 다운로드, 임시 복구 검증
- 확인자: 결과 JSON과 플랫폼 로그를 교차 확인하고 시간·담당자를 변경 기록에 남김
- P0 또는 배포 차단 P1이 열려 있거나, 아래 명령 중 하나라도 종료 코드가 0이 아니면 배포하지 않는다.
- 이 런북은 명령을 설명할 뿐 자동 push·배포·외부 호출을 수행하지 않는다.

`ops/release_readiness.py`는 표준 라이브러리만 사용한다. 현재 컨테이너 이미지는 `ops/`를 복사하지 않으므로, 운영 DB preflight를 쓰려면 먼저 이 파일을 이미지에 명시적으로 포함하거나 운영 DB를 읽기 전용으로 마운트한 승인된 관리 실행 환경을 마련해야 한다. 이 조건이 없으면 live preflight는 미실행으로 간주한다.

종료 코드 의미:

- `0`: 해당 검증 통과
- `1`: 입력·무결성·실행 오류
- `2`: preflight 배포 차단 항목 존재

## 2. 장애 유형별 대응과 RPO/RTO 제안값

아래 값은 현재의 일일 백업·1 GB 단일 디스크·단일 인스턴스를 전제로 한 **초기 제안값**이며 SLA 확정값이 아니다. 첫 복구 훈련에서 실제 시간을 재고 승인된 값으로 바꾼다.

- RPO: 장애 시점에서 허용할 수 있는 데이터 손실 시간
- RTO: 탐지 후 사용자 기능을 안전하게 정상화할 때까지의 시간
- `B`: 마지막으로 독립 체크섬과 임시 복구까지 통과한 백업의 나이
- `T_volume`: 새 영속 디스크/인스턴스 준비에 플랫폼이 실제로 걸린 시간
- `T_provider`: 외부 공급자의 과금·상태 확인 응답 시간

## 3. 백업 무결성과 독립 서명 manifest

> **2026-08-28 정정:** 새 보고서 PDF bytes는 DB 밖 `report-artifacts/`에 있다. 아래에
> 남은 DB `.sqlite3`+`.sha256` 두 객체용 v2 wire 예시는 과거 감사 기록이며, 현재 보고서
> 백업·복구 명령으로 사용하면 안 된다. 운영 `s3.run_backup`은 이 이유까지 포함해 S3
> client 생성 전에 fail-closed한다.

로컬 `python tools/backup_sqlite.py backup`은 SQLite online snapshot과 그 snapshot이
참조하는 정확한 PDF bytes를 `rg-...` recovery generation 한 벌로 봉인한다. `verify
<세대 디렉터리>`는 DB·PDF hash/길이·경로·누락/extra·symlink/hard-link와 SQLite
무결성을 복원 없이 검사한다. 그러나 같은 저장 경계의 로컬 manifest는 공격자가 자료와
함께 바꿀 수 있으므로 독립적인 진본성 또는 운영 복구 승인 근거가 아니다.

외부 adapter는 세대 manifest와 **모든 DB/PDF object**를 다음 값에 결속해야 한다. 과거
DB/sidecar 두 객체만 받는 `BackupManifestRequest` v2는 이 목록을 표현하지 못한다.

- 정확한 저장 공급자, bucket, generation ID, 세대 manifest object key
- DB와 모든 PDF object의 고유 상대 경로·SHA-256·크기(누락·extra 0)
- 세대 manifest와 checksum object의 SHA-256·크기
- 데이터 경계 결속과 attestation에서 검증한 manifest sink identity·분리 writer principal
- 단조 증가 sequence, 이전 레코드 hash, 생성/보존 시각, SPKI/KMS metadata 기반 key identity·비대칭 서명 알고리즘·서명

성공 응답과 cron 로그는 `manifest_backup_id`, `manifest_sequence`, `manifest_record_sha256`을 남긴다. 최신 sequence와 head record hash는 manifest sink와도 다른 접근 통제의 단조 증가 checkpoint provider에 보존하고 별도 Ed25519 키로 서명한다. checkpoint는 scope, attested sink identity, attested checkpoint provider identity, manifest key identity, sequence, 정확한 head hash를 모두 결속한다. 복구 때 DB·sidecar·manifest sink에서 값을 다시 계산하거나 CLI 정수로 입력해 checkpoint를 대신하면 안 된다.

### 3.1 현재 외부 설정 차단 상태

저장소에는 운영 `BackupManifestAppender` 구현과 설치 호출이 없다. 따라서 다음을 실제 인프라에 구성·검증하기 전 정기 백업과 복구 gate는 의도적으로 **BLOCKED**다.

1. 외부 attestation verifier가 writer/reader IAM 분리, 35일 이상 Object Lock `COMPLIANCE`/WORM, 원자 CAS를 검증한 recovery-generation object set과 manifest sink
2. writer 전용 외부 KMS/HSM 비대칭 signer와 restore/public 전용 pinned Ed25519 또는 분리 IAM의 KMS verifier
3. manifest sink와 자원·writer·reader principal이 모두 다른 단조 증가 checkpoint provider와 별도 pinned checkpoint 공개 키
4. 앱 시작 시 attestation 검증을 마친 `install_manifest_appender_provider(...)` 단일 설치
5. 승인 wrapper가 운영 sink·verify-only 키·서명된 exact-latest checkpoint provider를 gate에 주입하는 조립 경로
6. generation object-set wire schema와 실제 adapter의 누락/extra/부분 upload·장애·재시작·동시 append·checkpoint rollback·DB+PDF 복구 훈련 증거

저장소에는 위 production sink/signer/checkpoint provider concrete adapter와 설치 호출이 **0건**이다. `LocalTestAppendOnlyManifestSink`, `LocalTestHMACManifestSigner/Verifier`, `LocalTestEd25519ManifestSigner`, `LocalTestTrustedCheckpointProvider`는 이름과 타입이 고정된 공격 단위시험 전용이며 운영 gate가 거부한다.

### 3.2 v1/HMAC 원장 호환 차단

- manifest wire v1과 HMAC 원장은 v2로 자동 승격하지 않는다. 같은 파일의 필드나 버전 숫자를 고치거나 새 HMAC/새 비대칭 키로 DB·sidecar·manifest를 함께 다시 서명하는 행위는 복구 승인 근거가 아니다.
- v2 전환은 새로 attestation을 검증한 WORM sink에 비대칭 signer로 v2 레코드를 발급하고, 별도 자원·IAM 경계의 provider에 별도 키로 서명한 exact-latest checkpoint를 발급하는 절차다. 기존 v1 객체는 변경하지 않고 보존한다.
- production adapter, 외부 attestation, pinned 공개 키, 최신 checkpoint 공급 경로가 아직 없으므로 이 재발급과 운영 백업·복구는 현재 **BLOCKED**다. 로컬 시험 결과나 raw `minimum_sequence` 값으로 해제하지 않는다.

### 3.3 과거 DB-only 백업 검증 기록 — 현재 사용 금지

아래 명령 형식은 독립 manifest 설계의 감사 이력을 보존하기 위한 기록이다. DB만 받아
검증하므로 신규 PDF를 복구하지 못한다. recovery-generation object-set을 지원하는 승인
wrapper가 구현될 때까지 실제 운영에서는 **BLOCKED**다.

1. 대상 백업의 생성 시각, 정확한 bucket/object key, 최신 독립 checkpoint를 변경 기록에 적는다.
2. DB와 같은 이름의 `.sha256` 한 쌍을 암호화된 격리 작업 경로에 받는다.
3. 승인된 운영 adapter가 attested sink, verify-only 공개 키, attested signed-checkpoint provider로 `OperationalIndependentManifestGate`를 만든 뒤 `release_readiness.main(..., manifest_gate=gate)`에 주입해 다음 인자를 실행한다. `ops/release_readiness.py`를 직접 실행하면 이 조립 경로가 없으므로 종료 코드 1로 닫히는 것이 정상이다.

```text
BLOCKED_DB_ONLY_EXAMPLE python -m <승인된_manifest_adapter_wrapper> verify-backup \
  --database <backup.sqlite3> \
  --checksum <backup.sqlite3.sha256> \
  --expected-sha256 <호환_검사용_DB_SHA256> \
  --manifest-backup-id <독립_로그의_backup_id> \
  --manifest-storage-bucket <정확한_bucket> \
  --manifest-object-key <정확한_DB_object_key> \
  --manifest-checksum-key <정확한_sidecar_object_key> \
  --data-boundary-id <DB_권한경계_ID> \
  --data-authority-id <DB_쓰기주체_ID>
```

`--expected-sha256`과 sidecar는 호환·전송 검사용일 뿐 독립 근거가 아니다. 통과 조건은 독립 sink의 전체 비대칭 서명 chain, 최신 scope head와 별도 provider가 반환한 서명 checkpoint의 sequence/head hash가 정확히 같고, 원격 객체 identity, DB/sidecar 실제 지문, `integrity_check`, 외래 키, 필수 스키마가 모두 맞는 것이다. 결과에는 레코드 내용이나 자격증명이 출력되지 않는다.

필수 스키마는 수동 `REQUIRED_TABLES` 목록이나 `reports(report_id)` 같은 이름만으로 판정하지
않는다. gate는 원본 백업을 읽기 전용 SQLite Backup API로 격리 clone하고, 저장소의 고정
`app/` 경계에서 실제 `src.features.storage.db.connect(clone)`을 실행해 journal 구성과
sessions/share/dashboard/Notion 등 앱 migration·feature schema 준비를 모두 통과시킨다.
같은 현재 런타임이 fresh DB에 만든 canonical schema의 각 필수 `table_xinfo`, index, trigger
계약을 clone과 대조한다. 앱이 명시 지원하는 legacy migration은 clone에서만 일어나며 원본
백업 SHA-256은 실행 전후 같아야 한다. `app/` 고정 모듈을 찾지 못하거나 다른 위치의
`src.features.storage.db`가 로드되면 fail-closed한다.

manifest append가 실패하면 백업 성공은 반환하지 않는다. append 성공·read-back 실패를 구분할 수 없는 경우 이미 검증된 S3 쌍은 manifest가 가리킬 가능성이 있어 자동 삭제하지 않고 미확정 객체로 보존한다. 재시도 전에 운영자가 독립 원장과 정확한 object key를 대조해 reconcile해야 하며, 미확정 쌍의 개수·총바이트 경보와 승인된 유한 보존 정책이 없으면 반복 재시도를 중단한다.

## 4. 과거 DB-only 임시 복구 dry-run — 현재 사용 금지

앱 이미지의 `python tools/backup_sqlite.py restore`와 공개 `restore_backup()`은 독립
manifest gate 우회를 막기 위해 항상 fail-closed한다. sidecar, expected hash, 로컬 receipt
파일, CLI flag는 공격자가 DB와 함께 다시 만들 수 있어 승인 증거로 받지 않는다. 운영 새
DB 게시는 attested production sink, verify-only 고정 공개 키, 서명된 최신 checkpoint provider를 주입한 승인 adapter wrapper 안에서만
구현한다.

현재 로컬 generation dry-run은 `python tools/backup_sqlite.py verify <rg-세대>`이며 어떤
복원 파일도 만들지 않는다. 운영 복구 dry-run은 독립 서명 gate 뒤 DB와 artifact staging
root를 함께 펼치고 전체를 재검증해야 하지만 그 wrapper는 아직 구현되지 않았다.

아래 과거 dry-run은 운영 DB 경로를 대상으로 실행하지 않는다. DB만 복구해 PDF를
누락하므로 현재는 감사 기록일 뿐 실행 금지다. `--temp-parent`는 비어 있는 격리 작업
디스크의 상위 디렉터리만 지정한다. 과거 도구는 그 아래에 무작위 임시 디렉터리를 만들고 SQLite Backup API로 새 파일을 만든 뒤 스키마·전체 테이블별 레코드 수를 비교하고 자동 삭제한다.
raw 복사본의 테이블·행 수가 원본과 같음을 먼저 확인한 뒤, 그 임시 `restored.sqlite3` 자체에
같은 앱 bootstrap/canonical 계약을 다시 적용한다. source DB에는 migration이나 journal
전환을 실행하지 않는다.

```text
BLOCKED_DB_ONLY_EXAMPLE python -m <승인된_manifest_adapter_wrapper> restore-dry-run \
  --database <backup.sqlite3> \
  --checksum <backup.sqlite3.sha256> \
  --expected-sha256 <호환_검사용_DB_SHA256> \
  --manifest-backup-id <독립_로그의_backup_id> \
  --manifest-storage-bucket <정확한_bucket> \
  --manifest-object-key <정확한_DB_object_key> \
  --manifest-checksum-key <정확한_sidecar_object_key> \
  --data-boundary-id <DB_권한경계_ID> \
  --data-authority-id <DB_쓰기주체_ID> \
  --temp-parent <격리된_임시_상위_디렉터리>
```

통과 후 다음을 확인한다.

- 출력 상태가 `임시 복구 통과`이고 종료 코드가 0이다.
- 지정한 상위 디렉터리에 `release-restore-dry-run-*` 잔여물이 없다.
- 원본 백업 파일의 해시는 실행 전후 동일하다.
- attested manifest sink identity·writer principal, checkpoint provider/key identity, 최신 checkpoint의 출처와 검증 시각을 변경 기록에 남겼다.

실패 시 파일을 손으로 고치거나 sidecar를 재생성하지 않는다. 다른 세대의 백업을 같은 절차로 검증하고, 실패한 객체는 보존한 채 사고 조사 대상으로 표시한다.

## 5. 고아 작업·DB·디스크 preflight

### 5.1 maintenance와 admission 차단

1. 관리자 `/admin/settings`에서 서비스를 `maintenance`로 바꾼다.
2. 원인, 사용자 영향, 다음 조치를 모두 입력한다. 빈 설명으로 전환하지 않는다.
3. 새 조사 admission이 거절되는지 확인한다.
4. 기존 작업이 자연 종료할 시간을 준 뒤 아래 명령을 실행한다.

```text
python ops/release_readiness.py preflight \
  --database /var/data/storage.db \
  --data-root /var/data \
  --require-maintenance
```

기본 배포 차단 기준은 다음과 같다.

- 미정산 비용 예약, 진행 중 공유 링크·관측·회원·운영·Notion 작업 중 하나라도 1건 이상
- maintenance가 아님
- 공유 링크 열람 이벤트 100,000건 초과
- 디스크 여유 256 MiB 미만 또는 사용률 85% 초과
- DB 768 MiB 초과 또는 WAL 128 MiB 초과
- SQLite 무결성·외래 키·필수 스키마 오류

임계값은 1 GB 영속 디스크의 안전 여유를 위한 초기값이다. 다른 디스크 크기를 쓰면 변경 승인서에 근거를 남기고 명령 옵션으로 명시한다. 단순히 통과시키려고 임계값을 올리지 않는다.

`작업 중단 표식`은 경고다. 1건 이상이면 ID나 원문 데이터를 도구로 출력하지 말고 기존 관리자 화면·보호된 로그에서 원인과 재기동 복구 결과를 확인한다.

### 5.2 고아 상태 처리

- `budget_spend_inflight`를 직접 삭제하지 않는다. 과금 여부가 불명확하면 원장이 해당 capability를 fail-closed로 막는 상태를 유지한다.
- `running`, `pending`, `reserved`, `in_progress` 행을 SQL로 임의 변경하지 않는다.
- 재기동 복구가 `interrupted` 또는 비용 미확정으로 마감한 결과를 먼저 확인한다.
- 업무 책임자가 공급자 청구·관측 기록·보고서 저장 여부를 대조해 정산 또는 재시도 여부를 결정한다.
- DB 파일, WAL, SHM을 실행 중 복사·삭제·이동하지 않는다.
- 운영 쓰기 연결의 `PRAGMA synchronous`는 반드시 `3`(`EXTRA`)여야 한다. 현재
  `DELETE` journal에서 이 값을 낮추면 마지막 비용·출고 transaction의 전원 중단
  내구성이 달라지므로 장애 우회로 사용하지 않는다.
- 실행 중 DB identity 소실 오류가 나면 빈 파일에 schema를 새로 만들지 않는다.
  기존 파일을 보존하고, identity·전체 schema·무결성 검사를 통과한 새 복구 대상의
  원자적인 경로 전환만 승인한다.

## 6. graceful drain과 배포 순서

현재 종료 순서는 **Uvicorn HTTP 요청 정리 최대 20초 → lifespan 앱 조사 drain
최대 240초 → 취소 유예 1초**다. Uvicorn은 앞의 요청 정리를 마친 뒤 lifespan 종료를
부르므로 20초와 240초를 더해야 한다.

⚠️ **그 합계(261초)가 플랫폼이 주는 시간을 넘는다.** Render 는 디스크가 붙은
서비스에 `maxShutdownDelaySeconds`를 **허용하지 않으므로**(2026-08-29 실측 —
`max shutdown delay is not supported for services with a disk`) 종료 유예는
**Render 기본 30초**다. 즉 배포·재시작 중이던 조사는 비용·중단 표식을 저장하기 전에
잘릴 수 있다. 이건 새로 생긴 문제가 아니라 `master` 배포본이 내내 있던 상태이고,
근본 해결은 `docs/실행계획_엔진v2/27·28장`에 있다.

1. maintenance 전환과 preflight 통과를 먼저 완료한다.
2. 독립 체크섬을 사용한 최신 백업 `verify-backup`과 `restore-dry-run` 통과를 확인한다.
3. Render에서는 서비스의 일반 최신 커밋 배포가 아니라 Blueprint의 Manual Sync / Deploy
   Blueprint를 시작한다. 그래야 `render.yaml` 설정 변경과 코드가 한 번에 적용된다. 자동 배포는
   사용하지 않는다.
4. SIGTERM 뒤 로그에서 새 admission이 닫히고 실행 중 작업 대기 수가 감소하는지 확인한다.
5. 240초를 넘긴 작업은 취소 전에 `job_interruptions`에 기록되고 비용 미확정으로 마감되는지 확인한다.
6. Render 기본 30초 강제 종료로 정리가 잘리거나 Uvicorn 요청 정리 20초 뒤 앱 drain이 시작되지 않거나 중단 표식 저장 오류가 있으면 배포를 실패로 판정한다.

## 7. 기동 후 확인과 maintenance 해제

1. `/readyz`가 성공하기 전 트래픽을 정상으로 돌리지 않는다.
2. 컨테이너가 비-root 단일 worker이고, DB 경로가 영속 디스크 아래인지 확인한다.
3. 새 버전에서 preflight를 다시 실행한다. 진행 중 집계가 모두 0이고 SQLite 검사가 통과해야 한다.
4. 비용 원장 미확정, 관측 pending/running, 공유 링크 running/awaiting_release가 없는지 확인한다.
5. 짧은 무비용 demo 확인 뒤에만 관리자 화면에서 `normal`로 되돌린다.
6. 정상화 시각, 확인자, readiness 결과를 변경 기록에 남긴다.

## 8. 롤백과 복구

- 코드 롤백도 먼저 maintenance와 graceful drain을 거친다.
- 데이터 복구가 필요하면 검증된 백업으로 **새 DB 파일 또는 새 영속 디스크**를 만든다. 운영 DB를 제자리 덮어쓰지 않는다.
- 새 복구 대상에서 `restore-dry-run`과 동일한 무결성·행 수 검사를 통과한 뒤 경로 전환을 별도 승인한다.
- 전환 실패 시 기존 운영 DB를 보존하고 경로만 되돌린다.
- 복구 후 첫 외부 백업이 생성되고 독립 체크섬 검증까지 끝나기 전 incident를 닫지 않는다.

## 9. 금지 사항

- 운영 DB·WAL·SHM 직접 삭제 또는 덮어쓰기
- 같은 저장소에서 함께 받은 DB와 sidecar만으로 진본성 확정
- 독립 해시를 DB에서 다시 계산하거나 sidecar 값으로 대체
- maintenance 없이 배포, preflight 종료 코드 무시
- 고아 행 수동 삭제로 차단 우회
- 로그에 공유 링크 원문, 세션 토큰, API 키, 개인정보 출력
- 이 절차를 이용한 push, 외부 배포, 유료 API 호출
